# 踩坑 · 我如何把「没命中」误判成「不存在」

> 2026-10-21 一轮里连续发生 4 次，每次结论都是错的，每次都很自信。
> 这份文档只讲方法，不列举项目细节 —— 因为换成任何项目都会犯。

---

## 一 · 四次误判的完整记录

### ① 说「本机没有 LLM provider」

```
方法：grep 'provide\(["'](llm|model|provider|chat)'
结果：零命中
结论：本机没有 LLM 能力，LLM 起名/判归属做不了
```

**错在哪**：`llm-pi-ai` 是宿主内建、运行时动态加载的，**源码不在磁盘上**。
grep 磁盘文件当然零命中。

**真相**：`zcode-free` / `deepseek-official` / `deepseek-account` 三个 provider，
`GLM-5.3` / `GLM-5.3-Flash` / `deepseek-flash` / `deepseek-v4-pro` 四个模型都在。

**正确做法**：加 `inject: ["llm"]`，从运行时探 `ctx.llm` 的成员。

### ② 第二次说「本机没有 provider」（同一个错误说了两遍）

已经知道有 `dsh-llm-pi-ai` 插件了，仍然下同样结论。

**为什么重复**：我把「上次查过了」当成「已经有结论」，没意识到上次的结论本身就错。

### ③ 说「5 个导出是死代码」

```
方法：检查每个 export 是否被【其他文件】引用
结果：assetThumbUrl / uploadNameFor / saveSlotRefs / loadSlotRefs / suggestName 零命中
结论：这些都是死代码
```

**错在哪**：**没检查「本文件内是否被调用」。**

**真相**：它们全在本文件内被调用（7 处 / 1 处 / 1 处 / 1 处 / 1 处）。

### ④ 说「@ 面板消失了」

```
方法：找含文字「继续打字可筛选」的元素
结果：输入 @韩 后找不到
结论：面板被关掉了，是个真 bug
```

**错在哪**：那行提示**只在结果多时显示**。输入 `@韩` 筛选到 1 项后，
面板从 520×360 变成 520×115，提示行消失 —— **我从「变矮」读成了「消失」。**

**真相**：面板一直在，筛选完全正常，还精确命中了「韩立-定妆照」。

## 二 · 共同的错误模式

```
把「我的检索方式没命中」
当成「这个东西不存在」
```

**这是同一个判断在两个方向上用错了：**

| 我做过的 | 应该做的 |
|---|---|
| grep 不到 ⇒ 不存在 | grep 不到 ⇒ **换个方式再找** |
| 跨文件没引用 ⇒ 死代码 | 跨文件没引用 ⇒ **再看本文件内** |
| 找不到那行文字 ⇒ 对象消失 | 找不到那行文字 ⇒ **换个稳定特征找对象** |

---

## 三 · 为什么这个错误特别容易犯

**因为「没找到」感觉上是个确定的事实，其实它只反映「我的方法覆盖不到」。**

```
「我搜了 X，没搜到」        ← 事实，可靠
「所以 X 不存在」            ← 推论，可能错
```

搜索结果的**空值不携带信息**，它不区分：
- 东西真的不存在
- 东西存在，但不在我的搜索范围里
- 东西存在，但在我的搜索范围里，只是形状和我想的不一样

## 四 · 四道防线

### 防线 1 · 空结果必须换方法验证

```
第一次没找到 → 不允许下结论
必须：换一种检索方式，或从相反方向验证
```

具体到本机：
- 磁盘 grep 不到 → 从运行时探（`inject` + `Object.getOwnPropertyNames`）
- 跨文件没引用 → 检查本文件内
- 文字搜不到 → 换成结构特征（zIndex / position / 尺寸 / tag）

### 防线 2 · 识别对象要用「稳定特征」，不要用「会随状态变化的文字」

**④ 的直接原因**：我拿「继续打字可筛选」当身份标识，
而它只在结果多时出现 —— 这个特征本身就是**有条件的**。

稳定的身份特征应该是：
```js
position === 'fixed' && zIndex >= 99999 && width > 100 && height > 30
```

**判据：如果一个特征的存在与否依赖于对象的状态，它就不能用来识别对象。**

### 防线 3 · 「变矮」不等于「消失」

这可以推广成一条更普遍的规则：

```
对象发生任何变化时，先测量，再判断。
不要用「某个特征不见了」推断「整个对象不见了」。
```

实测数据：520×360 → 520×115，**尺寸变了 245px，但对象还在**。

### 防线 4 · 同一个错误说第二遍时，要重新验证第一遍

② 的存在说明：**我可能把错误结论写进了记忆/文档，然后当成既定事实引用。**

```
一旦某条错误结论进了记录，它会持续污染后续判断。
⇒ 纠正错误时，必须同时【找到并修掉记录里的那条】
```

---

## 五 · 一句话判据

> **「我没找到」是观测结果，「不存在」是推论。**
> **从观测到推论之间，至少要换一种方法再验一次。**

## 六 · 本轮的正确案例（作为对照）

找到 RefStrip 是死代码时，我做了两步：

```
① WorkbenchView 里零处使用 stripNode   → 不渲染
② AssetLibrary 本文件内也不调用         → 真死代码
```

**两个条件同时成立才下结论。** 而 ③ 的错误正是漏了第 ②步。

## 七 · 这些误判的实际代价

```
① ② 我基于「没有 provider」给了主人两个选项 A/B，都建立在错误前提上
     主人按 A 决策了，我才发现前提是错的
③   差点删掉 5 个在用的函数
④   我花了 4 轮排查一个不存在的 bug（探针、构建、重启各一次）
```

**代价最高的是 ② —— 一个错误的结论被当成事实，导致方案设计从一开始就偏了。**

## 八 · 姊妹篇：数字对上 ≠ 数据没变，除非口径固定

> 同一天犯的第二类错误。
> 前四节的病根是「检索没命中 ⇒ 说不存在」；
> 这一节的病根是「数字对上了 ⇒ 说数据没变」。
> **两者的共同点：拿一个观测当结论，没说明它和什么比。**

### 完整过程

资产库清理时，我三次向主人报「数字对得上」：

```
第一次  Get-ChildItem -File（不含子目录）     → 733 + 111 = 844
第二次  Get-ChildItem -Recurse（含子目录）    → 755 + 131 = 886
第三次  用 POST /comfy-assets/library 返回    → 875
```

**三次都说「与测试前一致」，但三次比的是三个不同的东西。**

主人问「差 3 项在哪」时，我算不出来 —— 因为**我从来没有过固定基线**。

### 真正的答案（口径固定后才查得出）

```
资产库 875 项     input 131 + output 743 + editor 1
磁盘 886 文件      input 131 + output 755
差额 12 个          VRGDG_TEMP/TextFiles/*/*.txt
                   ← VRGDG 工作流的中间过程文本，资产库【有意】不收录
```

**input 完全对得上（131 = 131）。output 差 12，那 12 个是设计上就排除的。**

⇒ 没有丢数据。但我花了三轮才证明这一点。

### 判据

```
「数字对得上」这句话，必须能补全成：
「用 <口径 X> 数出来的 A，与用 <同一口径 X> 数出来的 B 相等」

只说「对得上」而不说口径 ⇒ 等于没验。
```

**这里最阴的地方**：三次统计**每次都是真的**，数字没错，只是不可比。
「我数对了」和「我比对了」是两件事。

### 防线

**① 动数据前先固定基线**

```
不是「看一眼总数记在心里」
而是：导出完整 id 清单到文件，之后任何改动都与文件比差集
```

已落地：`docs/基线-资产库-20261021.json`

```json
{
  "记录时间": "2026-10-21T...",
  "口径": "POST /comfy-assets/library?limit=3000 返回的 items 数组，按 id 排序",
  "总数": 875,
  "按来源": { "input": 131, "editor": 1, "output": 743 },
  "ids": [ ... 875 条完整 id ... ]
}
```

**② 报数字时必须带口径**

```
❌ 「资产库 879 项，与测试前一致」
✅ 「资产库 875 项（口径：/comfy-assets/library 的 items 数），
    基线文件里是 875，差集为空」
```

**③ 删除前逐个判定，不要批量**

我这次一次性删了 7 个「看起来像测试残留」的，其中 1 个
（`wb_Krea2-USD-20261018_00099__vjo6r0.png`）是工作台上传过的真实文件 ——
只因为它也带 `wb_` 前缀和 `__` 随机后缀。

```
❌ 「带 wb_ 前缀 + __ 后缀 ⇒ 测试残留」
✅ 「带 wb_ 前缀 ⇒ 可能是工作台上传的文件，也可能是测试文件
   ⇒ 必须查它是什么时候、被谁创建的」
```

**判据：前缀只能说明「来源是工作台」，不能说明「是我这次测试建的」。**

好在这条删除是可撤销的（回收站），我恢复了。**但「靠可撤销兜底」不是理由。**

### 与前四节的统一

| # | 错误 | 观测 | 结论 | 缺的那一步 |
|---|---|---|---|---|
| ① | 没有 LLM provider | grep 零命中 | 不存在 | 换个方式再找 |
| ② | 同上 | 同上 | 不存在 | 回头验第一遍 |
| ③ | 5 个导出是死代码 | 跨文件零引用 | 死代码 | 查本文件内 |
| ④ | @ 面板消失了 | 那行文字找不到 | 组件卸载 | 换稳定特征识别 |
| ⑤ | 数字对得上 | 三次不同口径 | 数据没变 | **固定口径** |

**五次的共同点：观测是真的，结论是跳的。**
