### 阻断级（3 个）

#### 1. 五个参数控件全是摆设（§6.25）

**症状**
界面上「画幅 / 尺寸 / 张数 / 放大模型 / 时长」五个控件都能点、能显示、能持久化，
但提交给 ComfyUI 的永远是工作流默认值。

**根因**
```js
// WorkbenchView.js 的 onGenerate
const params = { prompt, steps: Number(steps), toggles };
// 之后只补了 files / refLabels / refWarnings / steps2 / seed
// 从未补 aspect / megapixels / batch / seedvrModel / durationSec
```
grep 这四个字段在 `params` 上下文 → 零命中。

**为什么长期没被发现**
- 界面显示是对的（React state 更新了，看起来「改了」）
- 生成能成功（用默认值也能出图）
- 输出尺寸「看起来正常」（工作流默认 9:16 也合理）
- **只有对比「界面选的值」与「ComfyUI 收到的值」才能发现**

**发现方式**
复核子代理劫持 `window.fetch` 抓真实请求 body。

**修复**
```js
if (caps.aspect) params.aspect = aspect;
if (caps.megapixels) params.megapixels = Number(megapixels);
if (caps.batch) params.batch = Number(batch);
if (caps.seedvrModel && toggles?.seedvr) params.seedvrModel = seedvrModel;
if (caps.duration) params.durationSec = Number(durationSec);   // ★ 字段名是 durationSec，不是 duration
```

**端到端实测**
```
界面选 1:1 + 1K + 4 张
  → 节点 211: {"aspect_ratio":"1:1 (Square)", "megapixels":1.0}
  → 节点 210: {"batch_size":4}
  → 产物: 1024×1024，宽高比 1.000，1.05 MP
  → 一采 4 张 / 二采 4 张 / SeedVR2 4 张 = 总 12 张
```

#### 3. 重启丢数据（§6.18）

**症状**
重启后时间轴变成 `video(0)`，而磁盘上明明有 4 段。

**根因**
```js
const outDir = config.outputDir ?? path.join(process.cwd(), "outputs");
```
`process.cwd()` 是宿主进程的工作目录。`Start-Process` 起的 DSH 没指定
`-WorkingDirectory`，所以写到别处去了。

**为什么特别隐蔽**
服务不重启时内存里一切正常，只有重启才暴露。
我一天重启十几次，每次看到 `video(0)` 都以为是「这次没数据」。

**修复**
```js
const HERE_DIR = path.dirname(fileURLToPath(import.meta.url));
const WORKSPACE_ROOT = path.resolve(HERE_DIR, "..", "..", "..");
// 并且兜旧路径：按优先级找第一个真的有 timeline-state.json 的目录
//   1. 工作区根/outputs  2. 插件包目录/outputs  3. process.cwd()/outputs
```

**实测**
重启后 `video(4)` / 540 条 / handoff 存活 / exportable=true。

## 四、三类「不报错」的失效模式

这 11 个缺陷里，7 个属于这一类，共性极强：

```
① 控件是摆设
   界面 state 变了，但没进 params
   检查方式：劫持 fetch 抓 body / grep params\.<字段> 与 UI 控件清单比对

② 静默跳过
   ComfyUI 遇到输入指向缺失节点，不报错，直接跳过该节点与下游
   检查方式：必须查 /history/<id>.outputs 的键，不能只看提交有没有报错

③ 静默清零
   存档坏了当空处理，下次写入覆盖
   检查方式：坏存档要隔离，reason 里带上备份路径
```

**这三类的共同点：眼睛看界面看不出来，只能对比「预期」与「实际」。**

## 五、子代理派发的教训

```
第一次派 tester（角色）          → 无产出，send_message 报 active teammate not found
第二次派 subagent（复杂任务）    → 只写了文件头就结束
```

## 十、「成对字段」排查（2026-10-19，防 §6.27 同类）

§6.27 的根因是「view 与 pos 语义上必须一起存在，但只恢复了 view」。
按这个模式，我把工作台里其它「成对字段」逐个查了一遍。

### 查到 4 组，3 组正常，1 组是有意取舍

| 成对字段 | 是否一起处理 | 结论 |
|---|---|---|
| `view` + `pos`（画布） | ✅ 修复前是分开的 | **已修**（§6.27） |
| `files[slot].role` + `files[slot].base64` | ✅ 前端先用，再转文本 | 不是缺陷 |
| `toggles[name]` + `steps2` | ✅ steps2 只在二采开时传 | 不是缺陷 |
| `job` + `promptId` | ✅ 同一对象里 | 不是缺陷 |

### 第 2 组的细节（原本我以为是缺陷）

```js
// WorkbenchView.js
1107 行: params.files[slot] = { base64: f.base64, filename: f.filename };
                                            ↑ 没有 role

1114-1123 行:
  if (modeId === "yz") {
    const refs = ... .map(([slot, f]) => ({ ..., role: f.role || "appearance" }));
    const { lines } = tagReferences(refs);
    params.refLabels = lines;   ← role 已经转成 <Subject N> 文本了
  }
```

**`role` 是前端消费的中间字段，不是后端要的。**
后端只读 `params.refLabels`（拼好的 H3 标签文本）。
⇒ `files[slot]` 不带 role 是有意设计，不是漏传。

### 第 3 组的细节

```js
1130 行: if (caps.steps2 && secondPassOn) params.steps2 = Number(steps2);
```
**二采关掉时不传 steps2** —— 这是 §3.13 ① 修过的缺陷（关了还传会导致
「工作流里找不到 node=221」）。当前写法正确。

### 第 4 组：sessionStorage 的持久化字段

```js
// 1073-1076 行
savePersisted({
  modeId, prompt, negative, aspect, durationSec,
  steps, steps2, batch, megapixels, seedvrModel, seed, toggles,
});
```
**12 个字段与 params 一一对应。** `files`（含 base64）故意不存 ——
大对象会撑爆 sessionStorage 配额，这是正确取舍（素材要重选，参数不用）。

### 结论

**§6.27 那种「字段应该成对但只恢复了一半」的问题，工作台里只出现在画布这一处。**
其余三组要么是有意设计，要么已被之前的修复覆盖。

## 十二、后续补充的 17 个缺陷（第 108-129 轮）

> 前三批 11 个见 §一。这里记后续靠「主动测异常路径 + 独立质检 + 扫描回潮」发现的。

### 独立质检员（tester 角色）两轮打穿 8 项

**第一轮（SHA256=74A1DA09…）**

| # | 发现 | 根因 | 修法 |
|---|---|---|---|
| 1 | `U+2800` 盲文空白能过 | 黑名单正则不包含 So 类 | 见下方「方法换了」 |
| 2 | `U+00AD` 软连字符能过 | 同上（Cf 类） | 同上 |
| 3 | 混合串 `\u2060\u2800\u00ad\ufeff` 也过 | 名单内的被删、名单外的独自变成「有效内容」 | 同上 |
| 4 | 槽名校验被 `continue` 整条跳过 | `if (!payload?.base64) continue` 在槽名检查之前 | 槽名检查提前 |
| 5 | `BM/RIFF/ID3` 纯文本冒充媒体 | 魔数只看前 2~4 字节 | 查文件结构 |
| 6 | base64 容差 ±4 放过 5 个非法字符 | `Math.abs(len*0.75 - buf.length) > 4` | 精确算期望字节数 |
| 7 | `filename` 覆盖别人的文件 | 原样透传 + `overwrite=true` | 扩展名白名单 + 随机前缀 |

**★ 第 1-3 条最重要的判断**：

> 「不是漏列几个字符，是黑名单方法本身失效。」

证据：混合串穿透说明**名单内的被删、名单外的留下来独自变成「有效内容」**。
⇒ 改用白名单（`\p{L}\p{N}\p{P}\p{S}` + 少量例外）。

**第二轮（SHA256=18674B63…）**

| # | 发现 | 修法 |
|---|---|---|
| 8 | 16 字节垃圾 PNG 也能过 | PNG 查宽高 + IDAT + IEND |
| 9 | 提示词无长度上限（1MB/10MB 都接受） | 上限 20000 字符 |
| 10 | **我改白名单时漏了 `\p{S}`，误拒 14 个符号** | 补 `\p{S}` |

**第 10 条是我自己造的**：`$ + = < > | ~ ^ ∑ ℃ √ ∞ ≈ ≠` 全被拒，报「提示词不能为空」。
根因：只写了 `\p{L}\p{N}\p{P}`，漏了 `\p{S}`（符号）。

> **白名单和黑名单的「列不全」是同一个错误，方向相反。**
> 黑名单漏了 → 该拦的没拦
> 白名单漏了 → 不该拦的拦了

### IEND 只查末尾 16 字节（我自己造的）

