```

### 6.33 不可见字符比想象的多：`\s` 只认 Zs 类（2026-10-19）

```
★ 6.32 说「去掉不可见字符」，第一版正则只列了 5 个：
    /[\s\u200b-\u200d\ufeff\u3000\u180e]/g

  实测还能穿透两个（我这轮自己测出来的）：
     \u3164  韩文填充符 HANGUL FILLER
             Unicode 类别是 Lo（字母），不是 Zs（空白分隔符）
             视觉上 ComfyUI 界面里完全空白，但 JS 认为它「有内容」
     \u0000  NUL 空字节
             类别 Cc（控制字符），同样不在 \s 里

★★ 根因：JS 的 \s 只匹配 Unicode 的 Zs（空格分隔符）+ 换行类（\n\r\u2028\u2029）。
   「视觉上不可见」和「Unicode 认为是空白」是两件事。

✅ 现在的正则（覆盖已知的所有类别）：
   /[\s\u200b-\u200f\u2028-\u202f\u205f\u2060-\u2064\u206a-\u206f
     \ufeff\u3000\u180e\u3164\u115f\u1160\uffa0\u0000-\u001f\u007f
     \ufff9-\ufffb]/g

   分段含义：
     \s                    所有 JS 空白（含 \t \n \r \f \v 和各种 Unicode 空格）
     \u200b-\u200f         零宽空格/非连接/连接 + LRM/RLM 方向标记
     \u2028-\u202f         行/段分隔符 + 各类窄空格（\u202f narrow no-break）
     \u205f                 中等数学空格
     \u2060-\u2064         word joiner + 函数应用/不可见乘号/分隔符/正号
     \u206a-\u206f         已废弃的格式控制字符
     \ufeff                BOM（粘贴常见）
     \u3000                全角空格（中文输入法常见）
     \u180e                蒙古文元音分隔符（旧的零宽）
     \u3164 \u115f \u1160 \uffa0   韩文填充符（4 个编码，都是视觉空白）
     \u0000-\u001f \u007f  C0 控制字符 + DEL
     \ufff9-\ufffb         中文/日文注音标记（视觉不可见）

★★ 纪律：
   1. 「看起来是空格」不等于「\s 能匹配」。
      枚举时按 Unicode 类别过一遍：Zs（分隔符）/ Cc（控制）/ Cf（格式）/ Lo（某些填充符）
   2. 每发现一个新的穿透字符，先补正则，再补 verify-text-guard.mjs 的用例
      —— 验收脚本里现在有 33 项 mustBeFalse，逐个编码都列了
   3. **不可能列全** —— 但每加一个实测抓到的，就永久挡住了

★ 实测验证（2026-10-19）：
   \u3164 / \u0000 / \u115f / \u2060 / \ufff9 / \u200f / \u2028  → 全部拒绝
   emoji 🐱 / 中文「一只猫」                                       → 全部通过（没误拒）

### 6.35 白名单也会「列不全」—— 漏了 \p{S} 误拒 14 个符号（2026-10-19）

```
★★ 这条是我自己打自己脸：上一节刚写完「校验设太严也是一种缺陷」，
   转头改白名单时就把这个缺陷造出来了。

❌ 第二版白名单：
     const VISIBLE = /[\p{L}\p{N}\p{P}\u{1F000}-\u{1FAFF}
                       \u{2600}-\u{27BF}\u{2190}-\u{21FF}
                       \u{2B00}-\u{2BFF} 货币符…]/u;

   ⇒ 实测这些全被拒，报「提示词不能为空」：
        $ + = < > | ~ ^ ∑ ℃ √ ∞ ≈ ≠    （14 个）

   ★ 为什么 * / @ # % & 能过？
     它们归 \p{P}（标点）。
     $ + = < > 归 \p{S}（Symbol，符号）。
     我写了 \p{L}\p{N}\p{P} 三兄弟，独独漏了 \p{S}。

✅ 修：补 \p{S}
     const VISIBLE = /[\p{L}\p{N}\p{P}\p{S}\u{1F000}-\u{1FAFF}]/u;
   （\p{S} 含盲文区段，那个在 hasVisibleText 里单独排除）

   实测后 41 项全对：符号 14 个不再误拒，不可见字符仍全拦。

★★ 教训：**白名单的「列不全」和黑名单的「列不全」是同一个错误，只是方向相反。**
   黑名单漏了 → 该拦的没拦
   白名单漏了 → 不该拦的拦了
   两者都是「没想清楚全集」。

★ 判据升级：
   不要问「白名单够不够」，要问「Unicode 的通用类别我列了几个？」
     L 字母  M 组合符  N 数字  P 标点  S 符号  Z 分隔符  C 控制/格式
   我这次只列了 L N P 三类，漏了 S（符号）与 M（组合符）。
   ⇒ 结论：**符号类字符在提示词里非常常见**（$ = + 用于强调、℃ 用于温度、
     ∑ √ ∞ ≈ 用于数学），不能当成「罕见特例」排除。

★★ 一条元教训：**改校验时，正反两组用例必须同时跑。**
   我这轮只测了「坏的能不能拦住」，没测「好的会不会被拒」——
   结果误拒 14 个符号，直到质检员指出来才发现。
   verify-bad-input.mjs 的 ⑤ 组「正常输入仍能通过」就是为这个存在的，
   但当时只放了「a cat」和「真 PNG」两个用例，覆盖不到符号类。

### 6.36 质检员的「固定基线」纪律（2026-10-19）

```
