## 一 · 可行性核实（先证明能做，再动手）

### ArtCraft 引擎的 API 是完整的

```
adapters, command, timeline, playback, scenes, project,
media, renderer, save, audio, selection, clipboard, diagnostics
```

关键能力（实测枚举出来的方法名）：

```
timeline   insertElement / splitElements / deleteElements / moveElements /
           duplicateElements / addTrack / removeTrack / updateElementTrim /
           updateElementRetime / toggleTrackMute / getElementsWithTracks
playback   play / pause / seek / getCurrentTime / getIsPlaying / subscribe
project    export / saveCurrentProject / listProjects / renameProject / subscribe
media      addMediaAsset / getAssets / loadProjectMedia
selection  setSelectedElements / getSelectedElements
command    undo / redo / canUndo / canRedo
renderer   setRenderTree / saveSnapshot / exportProject
```

⇒ **够。** 自建 UI 不需要上游的 React 组件，只需要这些 manager。
预览画面本身还是用上游的 canvas 渲染（`renderer` / `PreviewPanel` 里的画布逻辑），
但**外围的布局、工具栏、面板、菜单全部自己写**。

### 为什么这样做更好

| | 改上游 UI | 自建 UI |
|---|---|---|
| 样式冲突 | 要不断对付 Tailwind preflight / shadcn 变量 | 零冲突 |
| DSH 对齐 | 每处都要覆盖上游的类 | 直接写 DSH 的值 |
| 做减法 | 要藏上游的按钮 | 想要什么写什么 |
| 上游升级 | 我们的改动会被覆盖 | 不受影响 |

这正是主人第 1 条的意思。

## 二 · 预览区「大黑块」—— 根因已查明

**实测数据**：

```
project.settings.background = { type: "color", color: "transparent" }
canvas 的 computed 背景       = rgba(0, 0, 0, 0)      ← 透明
预览容器背景                  = rgb(255, 255, 255)   ← 白色
```

**根因**：画布本身是**透明**的，但每帧渲染时**没画任何东西**，
浏览器把透明区域显示为「什么都没有」——
而画布元素本身在页面上的默认呈现是黑色（离屏 canvas 的初始像素是透明的，
但很多渲染路径会把 clear 掉的颜色当成黑）。

⇒ 结果就是：空项目 = 一块纯黑。

**修法（三档，从轻到重）**：

```
A. 给 canvas 元素直接设 CSS 背景
   canvas { background: var(--dsw-alias-bg-layer-2) }
   —— 透明像素会透出 CSS 背景 ⇒ 显示成浅灰，不再是黑
   优点：一行 CSS，零风险
   缺点：导出时如果也走这个 canvas，会影响输出

B. 渲染前先清成画布背景色（用 project.settings.background.color）
   —— 但那个值是 "transparent"，清成透明还是黑

C. 空状态时【不渲染 canvas】，改显示一个占位
   —— 最符合 DSH 风格（refactoring-ui §8.4：空态要当作功能的一部分设计）

⇒ 采用 C + A：
   空项目时显示占位（图标 + 「把视频拖进来」+ 提示）
   有内容时才挂 canvas，并给它浅灰底
```

## 三 · 「默认上次导入内容」—— 现状是完全没有

**实测**：

```
localStorage 里只有 panel-sizes / assets-panel / dsh.* 主题相关
【没有任何】项目数据的持久化键
```

**但 adapter 是有的**：

```
adapters.js  projectStorage.loadProject(id)  → fetch('/timeline/snapshot')
             projectStorage.saveProject(p)   → onSave(...)
```

问题在 `saveProject`：

```js
if (typeof onSave !== "function") {
  log.warn?.("[artcraft] saveProject 没有 onSave 回调，改动未写回");
  return;   // ← 静默放弃
}
```

而 `onSave` 在 `client.js:448` 确实传了（`createTrimWriter`）。
**但它只写 trim（裁切），不写「有哪些片段」**。

⇒ 现在的语义是：
- **dsh-editor 的 timeline-state 是数据真源**（Agent 写这里）
- ArtCraft 只在保存时把 trim 写回去
- **ArtCraft 里新导入的片段，不会进 timeline-state**

所以「上次导入的内容」在刷新后就没了 —— 因为导入只在 ArtCraft 内存里。

**修法**：让 `saveProject` 把**完整的时间轴**写回 timeline-state，
而不只是 trim。这是数据层改动，需要设计好「谁是真源」。

## 四 · Agent 操作实时反馈 —— 现在完全没有

**实测**：
```
client.js 只有 watchDshTheme（每秒轮询主题）
没有轮询 /timeline/snapshot
没有 SSE / WebSocket
dsh-editor 没有 broadcast/emit 机制
```

⇒ **Agent 调 `timeline_add_shots` 加了三镜，UI 完全不知道。**

### 方案对比

| 方案 | 延迟 | 实现复杂度 | 可靠性 |
|---|---|---|---|
| **A. 轮询 `/timeline/snapshot`** | 1~2 秒 | 低 | 高（无状态） |
| B. SSE（Server-Sent Events） | 实时 | 中 | 中（连接断了要重连） |
| C. WebSocket | 实时 | 高 | 低（要心跳） |

**选 A**，理由：
1. dsh-editor 已经有 `/timeline/snapshot` 路由（`adapters.js:24` 在用）
2. 轮询 1 秒的成本可以忽略（返回的是 JSON，几 KB）
3. 无状态，断了自动恢复
4. 改动最小 —— 不需要动 dsh-editor 一行代码

**但要做得对**：

```
① 用 version / savedAt 判断有没有变化，没变就不重渲染
   （否则每秒全量重渲染，编辑器会卡）

② 变化要【呈现出来】，不能只是静默更新
   主人要的是「让用户知道 AGENT 操作了什么东西」⇒ 要有可见反馈

③ 反馈的形式（三种同时用）：
   · 变化的元素短暂高亮（1.5 秒渐变）
   · 右上角一条消息：「Agent 添加了 3 个片段」
   · 如果是生成类操作（timeline_generate），显示进度条

④ 区分「自己改的」和「Agent 改的」
   自己改的不需要弹提示（否则每拖一下都弹）
```

## 五 · 这也解释了为什么「自建 UI」是对的选择

上游的 UI 里**没有「Agent 操作反馈」这个概念** ——
它设计时假设「只有用户在操作」。

要在上游 UI 上做这件事，得在每个组件里插钩子。
自己写 UI 就简单了：一个顶层 hook 轮询 + 一个高亮层 + 一个消息条。

## 七 · 风险与取舍（如实说）

### 自建 UI 的代价

```
· 上游的 30+ 个面板组件全部不用了（素材/属性/文字/贴纸/特效/设置/字幕）
  ⇒ 哪些要自己重写？这是最大的工作量
· 音视频波形、缩略图条、关键帧曲线、遮罩编辑 —— 这些是硬活
  ⇒ 建议：第一版只做「能用」的轨道（色块 + 名称 + 时长），
    波形/缩略图后续再加
```

### 保留上游的部分（不重写）

```
· canvas 渲染管线（renderer）
· 音频播放（audio manager）
· 导出管线（export）
· 命令/撤销栈（command）
· 关键帧、遮罩、特效的【数据层】保留，UI 暂不做
```

⇒ 换句话说：**外壳自己写，引擎继续用**。

### 「上次导入恢复」的风险

```
现在 Agent 写 timeline-state，ArtCraft 写 trim。
如果 ArtCraft 也全量写回，两边会打架。
⇒ 必须先定「谁是真源」：

  方案 1（推荐）：timeline-state 是唯一真源
          ArtCraft 的改动 → 全量写回 timeline-state
          Agent 的改动 → 也写 timeline-state
          UI 轮询 timeline-state ⇒ 两边自动同步

  方案 2：各存各的
          更简单但会不一致，不推荐
```

## 八 · 需要确认的一件事

第 23 条（上次导入恢复）如果要按「方案 1」做，
就需要 **ArtCraft 每次改动都全量写回 timeline-state**。

这件事的**风险**是：写回的频率、体积、以及会不会覆盖 Agent 刚写的内容。

我打算这样做，请在实装时按此执行：
```
· 只写「时间轴结构」（有哪些元素、起止时间、引用哪个资产）
· 不写 Agent 的 shot/prompt/rendered 字段（那些是 Agent 的）
· 写之前先读一次，合并而不是覆盖
```
