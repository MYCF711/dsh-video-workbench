## caps 字段清单

共 8 个键：

| 键 | 值 | 类型 | 含义（按值推断） |
|---|---|---|---|
| `duration` | `false` | bool | 不支持时长 |
| `batch` | `true` | bool | 支持批量张数 |
| `steps` | `true` | bool | 支持一采步数 |
| `steps2` | `true` | bool | 支持二采步数 |
| `aspect` | `true` | bool | 支持画幅比例 |
| `megapixels` | `true` | bool | 支持像素量（MP）选择 |
| `seedvrModel` | `true` | bool | 支持 SeedVR2 模型（7B/3B）选择 |
| `secondPassToggle` | `"secondPass"` | string | 不是布尔能力，而是「二采开关映射到 `toggles.secondPass`」的指针 |

即：布尔能力 7 个（true 的 6 个 + false 的 `duration` 1 个），另有 1 个字符串映射键 `secondPassToggle`。

## toggles 字段清单

共 4 个键，全部 `type: "bool"`：

| 键 | label | default |
|---|---|---|
| `secondPass` | 二采精修 | `true` |
| `redraw` | 高清重绘（②组） | `false` |
| `loraChain` | 挂 LoRA | `false` |
| `seedvr` | SeedVR2 放大 | `false` |

`defaults` 是 5 个扁平标量：`prompt`（字符串样例提示词）、`aspect`（`"16:9"`）、`steps`（`8`）、`steps2`（`5`）、`batch`（`1`）。注意 `defaults` 里**没有** `megapixels`、`seedvrModel` 的值，也没有任何 toggle 的默认值（toggle 默认值在 `toggles.*.default` 里）。

## 结论

- 该工作流支持的能力项数量：**10 项**
  - 口径：`caps` 中值为 `true` 的布尔能力 6 项（`batch` / `steps` / `steps2` / `aspect` / `megapixels` / `seedvrModel`）+ `toggles` 中可切换的开关 4 项（`secondPass` / `redraw` / `loraChain` / `seedvr`）= 10。
  - 补充说明：`caps.duration` 为 `false`（不支持时长），`caps.secondPassToggle` 是字符串指针、不单独计为能力项。
  - 若只数 `caps` 里的键则有 8 个，但其中 1 个是映射指针、1 个是负能力，故不按 8 计。
- 我能否从 HTTP 层确认「这些控件在 UI 上排成一行」：**不能**
  - 原因：`/comfy-bridge/modes` 返回的是**数据契约**，只描述「有哪些能力、开关键名、默认值、提示文案」。响应里没有任何布局语义字段 —— 没有分组（section/group）、没有行号、没有控件宽度/顺序、没有 grid/row 标记。最接近顺序的 `order: 1` 是**标签页（tab）排序**（同级还有 `label` / `tabSub` / `primary`，明显描述的是 tab 而非 tab 内控件），`toggles` 的对象键顺序是 JSON 对象的书写顺序，V8 对字符串键保序，但**服务端保序 ≠ 前端按此顺序渲染成一行**。
  - 因此「9 个控件在同一行」属于**前端渲染层的事实**，HTTP 数据层无法证实也无法证伪。本结论**未验证**，需读前端参数区组件源码或截图核对实际 flex/grid 布局。
  - 顺带一处与「9 个控件」对不上的地方：本接口暴露的可渲染控件数按上表为 10 项能力（未计 `prompt` 文本框，若计入则 11 个可见控件）。「9」这个数字在本 JSON 里找不到直接对应 —— 除非把某个 toggle 或 megapixels 排除在外。这一点需要前端源码或截图才能定，我不替你补数字。
