# 深色模式暴露的 5 个 token 误用（2026-10-22 实测）

> ⚠ 本文原计划写入 Hindsight，但 2026-10-22 22:xx 时 `<HINDSIGHT_HOST>` 连接超时。
> 先本地存档，服务恢复后应 `hindsight_ingest_document` 补录。

主人一句话点破：「**换成深色后有点原形毕露了**」。

## 核心判据

**浅色下看不出差别的 token 用法，深色下会全部暴露。**
所以任何 `bg-layer-*` / 硬编码颜色的改动，都必须在**深色**下复查一遍。

## DSH 深/浅两档的实际值（实测 19499）

| token | 浅色 | 深色 |
|---|---|---|
| `--dsw-alias-bg-base` | `#ffffff` | `#151517` |
| `--dsw-alias-bg-layer-1` | `#ffffff`（**与 base 同色**） | `#232324` |
| `--dsw-alias-bg-layer-2` | `#f7f8f9` | `#2c2c2e` |
| `--dsw-alias-bg-layer-3` | `#f7f8f9` | `#353638` |
| `--dsw-alias-interactive-bg-hover` | 淡灰 | `#ffffff14` |
| `--dsw-alias-border-l2` | `#0000001a` | `#ffffff1f` |
| `--dsw-alias-border-l3` | `#0000001f` | `#ffffff29` |

★ 注意 `bg-layer-1` 在浅色下 = `#ffffff`，与 `bg-base` **完全同色**。
  所以「用 layer-1 做区块底」在浅色下看不出任何问题 —— 这正是它藏得住的原因。

## 五个真实错误

### ① 侧边栏用 bg-layer-2 → 深色下像贴了块补丁
```
浅色：canvas #fff   vs sidebar #f7f8f9   差 8  → 几乎看不出
深色：canvas #151517 vs sidebar #2c2c2e  差 23 → 明显的亮块
```
**修法**：侧边栏和画布**同底**，靠分隔线界定。
判据：**卡片用抬升层，分区用分隔线。** 侧边栏是「同一张工作台的另一半」，不是浮起的卡片。

### ② 硬编码 rgba(0,0,0,.035) 做预览底 → 深色下变成「更黑」
原注释写着「在暗色下也是淡灰」—— **这句话是错的**。
`rgba(0,0,0,.035)` 叠在 `#151517` 上只会更暗，预览空态等于消失。

**修法**：`--dsw-alias-interactive-bg-hover`
- 浅色下 = 淡灰（与面板可区分）
- 深色下 = `#ffffff14` 淡白（提亮）

**通用判据**：`rgba(0,0,0,α)` 只在浅色下是「灰」。要两个方向都对，
必须用会在深色下翻转成白色的 token（`interactive-bg-hover` / `border-l*`）。

### ③ 工具栏用 bg-layer-1 → 深色下成了一条深灰带
浅色下 layer-1 = base = `#fff`，无差别；深色下差 14，视觉上把界面切成两截。
**修法**：工具栏是「画布的一部分」，用 `bg-base` + 下边框。

### ④ 根容器背景用 bg-layer-1 → 同样亮一档
同上。

### ⑤ border: 0.5px 在 dpr=1 下会被取整成 1px
实测 `window.devicePixelRatio = 1`，`borderBottomWidth` 读出来是 `"1px"`。
DSH 的 composer 卡片用 `boxShadow: rgba(255,255,255,0.12) 0 0 0 0.5px` ——
**boxShadow 的 spread 不取整**，0.5px 就是 0.5px。
⇒ 要对齐 DSH 的视觉重量，用 boxShadow 而不是 border。

## 分隔线的真相（查证过程）

主人问「DSH原生对话框与画布直接是不是也少了分割线？DSH的对话tab中是有的」。

去 DSH 对话 tab 里逐层查了：
```
composerStack / composerSeat / scrollBody
  全部 borderTop: 0px、boxShadow: none、无 ::before/::after
```
**DOM 里没有独立的线元素。** 那条视觉分界来自 composer 卡片自己的
`boxShadow: rgba(255,255,255,0.12) 0 0 0 0.5px`（圆角 28 的描边）。

⇒ 所以「加一条分隔线」的正确做法不是画 border，
  而是让相邻元素各自有描边，靠描边的贴合形成分界。

## 间距的真相

实测剪辑台：`timelineBottom = 794`，`composerTop = 794` —— **完全贴合**，
中间既无间隙也无分隔 ⇒ 时间轴与输入框「糊在一起」。
修：底部 `padding: 8px` + 一条描边。

★ 注意验证方法：要量**内容**的边界（子节点的 bottom），不是容器的 bottom。
  容器的 bottom 会一直是 794（padding 在容器内部），我一开始量错还以为是没生效。

## 断言的二次教训

第一版断言我写的是「`background: rgba(`」，即**要求必须硬编码 rgba**。
改成 token 后断言变红，于是我放宽成 `token || rgba` ——
结果**变异测试证明这是假断言**：改回纯 rgba 仍然通过，而那正是要防的错误。

⇒ 收紧成「必须是 `--dsw-alias-interactive-bg-hover`」。
现在两种变异（改回 rgba / 改成 bg-layer-2）都能正确变红。

**判据：放宽断言时，要问「我放宽掉的，是不是正好是要防的那个错误」。**
如果是，那就不是放宽，是失效。

## 附：本轮其它实测

### 插件加载耗时（主人问「装上之后需要这么久才能启动 DSH?」）

不是。DSH 启动不受影响：

| 指标 | 值 |
|---|---|
| DOMContentLoaded | 158ms |
| load 事件 | 568ms |
| 我们的 bundle 在初始加载列表里吗 | **不在**（懒加载） |
| 点 tab（已缓存） | 105ms |
| 冷启动传输+解压 | 127ms |
| 文本解码 | 23ms |
| V8 解析（估） | 166ms |
| **最坏合计** | **约 320ms** |

那个「135 秒」是**构建产物**的时间（`node build.mjs` 要读 10.43MB base64 payload）。

### 热更新不生效

实测：改完源码、跑 build、刷新页面，`__DSH_BOOT__.entries[comfy-workbench].rev`
仍是旧值（`0544ddfe7f3e`）。**必须重启实例**才拿到新的 rev。

### 任务队列：后端早有，前端没接

`index.js:481` 的 job handler 一直返回 `queue: { running, pending, runningPromptId, pendingPromptIds }`。
前端 `renderResultBar` 只显示「运行中 · jobId」，**从没用过 queue**。
本轮补上「排队第 N 位」/「后面还有 N 个」。

★ 这是 AGENTS §6.38「生产方产出、消费方没接」的又一例。

⚠ 实时**进度百分比**拿不到：ComfyUI 的进度只在 WebSocket 的 `progress` 消息里，
而本项目没用 WebSocket，`/history` 只在结束时才有数据。
要做必须加 WS 客户端，不是前端能单独解决的。
