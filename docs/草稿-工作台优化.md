## 一 · 目标（会变，随手改）

> **v1（本稿起点，逐字来自主人）**
> - 「优化当前的产品也是一下项目，你应该按流程走，而不是自己干活」
> - 「这是一个优化项目，按流程从草图到方案开始走，按最小交付房间提交成果」
> - 「图片不能打开，不能保存，不知道对应的是哪个的产物」
> - 「现在的视频工作台部分是不是空白太多？弄成画布怎么样？生成后直接弹到画布里面？」
> - 「目标就是更好用的 agent 和用户可协同的，全自动图音视频工作台」

**收敛成一句**：把「UI 看到的东西」和「Agent 能拿到的东西」对齐到同一份**带来源的产物记录**上，并让用户在产物出现的第一秒就能看清、打开、保存、分辨。

> **R3 补一句边界**：本轮优化**不改生成质量本身**（那是 quality-room 的诊断 + 后续调参），只改「产物的呈现」「协同的形状」「剪辑与成片的能力」。

### A · 产物展示（主人点名的第一件事）

#### 设想 A1 · 产物加「来源角标」
- 内容：每张产物右上角标 `一采 / 二采 / USD / SeedVR2`，数据来自 `bind.outputs` 的语义 key 反查节点 id。
- 好处：直击「不知道对应的是哪个的产物」。
- ⚠ 坏处 / 代价：`bind.outputs` 只有 key→nodeId，没有中文标签。
- **R2 判**：**不坏，但要挡住两个坑**。① E20：只有 krea2 有 4 个语义 key，yz/qwen21/qwen21-edit 都只有 1 个 —— key 数量为 1 时不渲染角标。② E5：M1 现在**根本没把语义 key 传下去**，角标不能在前端靠文件名猜。⇒ 必须在 M1 补映射。
- **R3 判**：**采纳，成为 M1 的核心**。这是全方案唯一的「根」—— E4/E5/E8/E9 四条实测指向同一件事：产物缺一层元数据。角标不是装饰，是这层元数据的第一位用户。
- 状态：✅ **采纳**（→ M1）

#### 设想 A2 · 点图开 lightbox（原图 + 缩放 + 左右翻）
- 内容：点缩略图 → 全屏看原图，支持缩放、拖拽、方向键切换。
- 好处：直击「图片不能打开」。
- ⚠ 坏处 / 代价：要引 npm 包并过 esbuild IIFE 打包；部分库依赖 CSS。
- **R2 判**：**不坏**。`library_search` 实测有现成：`react-medium-image-zoom 5.4.9 / 430 万次/月`、`yet-another-react-lightbox 3.32.2 / 280 万次/月`。CSS 可在 IIFE 里当字符串注入（工作站 `AGENTS.md` §3.5 已记这条）。
- **R3 判**：**采纳**（→ M4）。选型留到实施时定，方案只锁「必须支持缩放 + 左右翻 + Esc 关闭」。
- 状态：✅ **采纳**（→ M4）

#### 设想 A3 · 下载按钮
- **R2 判**：~~**单独做必坏**~~。跨源时 `download` 属性被忽略；E10 实测带 `Origin` 的 GET 直接 403。⇒ 必须挂 A19 或 A20。
- 状态：~~已否决（作为独立设想）~~ → 并入 A19/A20 的验收项

#### 设想 A4 · 生成完成后自动「弹到」产物
- 内容：任务完成 → 成果区自动滚动/展开到新产物。
- 好处：直击「生成后直接弹到画布里面」的一半。
- ⚠ 坏处 / 代价：用户正在翻旧产物时被打断。
- **R2 判**：**不坏，但要限条件**。现在根本没有旧产物（E22），打断场景暂时不存在。⇒ 保留，A15/A16 落地时必须加「用户已手动滚动过就停止自动滚动」。
- **R3 判**：**采纳**（→ M3），并把它降级成「新批次出现时滚动到墙顶 + 一次 200ms 高亮」，不做浮层 —— 浮层会盖住参数区，与 §3.9 的「核心区留给成果」打架。
- 状态：✅ **采纳**（→ M3）

#### 设想 A5 · 产物墙（网格/瀑布流）替代线性排列
- 内容：把 `display:flex; flex-wrap:wrap` 改成自适应网格。
- 好处：直击「大片空白」。
- ⚠ 坏处 / 代价：只有 1 张产物时视觉更空。
- **R2 判**：**不坏**。1 张时 `minmax(240px,1fr)` 本就只占一格，与线性排列视觉差异为零。⇒ 保留。
- **R3 判**：**采纳**（→ M3）。E20 决定了列数规则：`outputs` 语义 key ≥ 4 → 固定 4 列并排；= 1 → 单列。

## 五之四 · R4 改写记录（★ 划掉的不删）

> R4 只做切分，但切分时暴露了两处需要改写的旧决定。按纪律：划掉 + 写新条目 + 记日志。

**#1 · ~~B5 参数指纹与 D5 Recipe 合并实现~~（R3 原判）→ 解耦**

- **R3 为什么那么判**：两者都是「把这次是怎么生成记下来」，看着是同一份数据。
- **R4 发现会坏在哪**：R3 说「与 B5 同一份数据，可共用」——但 B5 的指纹在 `dsh-comfy-bridge` 的 `jobs` 里（E22：**纯内存**，重启即丢），而 D5 的 Recipe 要跨会话复用（用户下个月还想套回这条提示词）。
  - 共用 ⇒ Recipe 的数据来源是一个**重启就没**的 Map ⇒ Recipe 存下来也没法校验「指纹对应的参数还在不在」。
  - 而 `dsh-editor` 的 `clip.shot` **本身就有完整参数**（实测 `timeline-state.json`：`{modeId, prompt, aspect, durationSec, steps, seed, toggles, media, history}`）且是**落盘**的。
- **改写为**：M6（Recipe）**不依赖 M1**，参数从 `clip.shot` 取；M1 的指纹只服务 M2 的元信息展示。
- **代价**：两处都会算一个「参数摘要」，但不共用代码 —— 因为它们分属两个包，共用要跨包 import（`dsh-editor` 与 `dsh-comfy-bridge` 是兄弟包，没有互相依赖）。跨包依赖会把两个模块焊死，违反判据②。
- **这是「重复」，但不是「重复造轮子」** —— 是两个包各自的 20 行摘要函数。共用它的接缝成本高于重复成本。

**#2 · ~~M1 与 M2（同源代理）拆成两个模块~~（R4 初稿想拆）→ 合并为一个 M1**

- **初稿为什么想拆**：source 映射（元数据）与 asset 代理（IO）是两件事，看着该分开。
- **R4 发现会坏在哪**：两者**都在 `dsh-comfy-bridge` 同一个包内**，且拆开后 M1a（元数据）单独交付时，主人**看不到任何东西**（curl 才有变化）。
  - `planning-draft` §5.2 的要求是「每完成一个房间就有可交付成果（好出成果）」。
  - 拆两个模块 ⇒ 两次验收、一次可见成果。
- **改写为**：合并成一个 M1「产物元数据与寻址」，验收里加一条**人可读的产物清单**（`curl` 输出直接列出「一采 = xxx.png / 二采 = yyy.png / ...」），这样 M1 交付时主人能亲眼看出来。
- **代价**：M1 稍大（两件事），但两件都服务同一个目标 —— **「产物可被识别与引用」**，那是同一个房间。
