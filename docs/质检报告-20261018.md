## 缺陷 1

- **严重度**：P1（功能坏）
- **标题**：「Qwen 改图」与「多参 H3」的参考素材**没有任何上传入口**，点生成直接拿工作流里硬编码的内置示例图跑
- **复现步骤**：
  1. 切到「Qwen 改图」工作流
  2. 观察参数条 —— 只有「工作流 / 张数 / 步数 / 种子 / 生成」，**没有参考图上传控件**
  3. 直接点「生成」
- **预期**：`qwen21-edit.bind.json` 的 `media` 声明了 `ref_image_0`（原图）、`ref_image_1`（参考图）；`yz.bind.json` 声明了 6 张参考图 + 1 参考视频 + 3 参考音频。这些槽位应当能在界面里上传/替换。
- **实际**：
  - 全包 grep `type: "file"` = **0 处**（`src/*.js`、`src/*.mjs`、`lib/client.js` 全查）
  - `WorkbenchView.js` 里 `params.files` 出现次数 = **0**
  - `bridge.generate()` 从不发 `files`
  - 点生成后 `POST /comfy-bridge/generate` 返回 `200 {"jobId":"comfy-mvdgzhg2-0hl1pp","promptId":"7a382ebb-...","nodes":16}`
  - ComfyUI `/history/7a382ebb-...` → `status_str: "success"`, `completed: true`，产物 `Qwen_image_2.1_00017.png`
  - **实际喂给模型的是工作流 JSON 里的默认值**：`qwen21-edit.json` 节点 470 `LoadImage.image = "portrait_model_denim.png"`、节点 475 `LoadImage.image = "clothing_light_blue_denim_shirt.png"` —— 作者内置的示例图
- **影响**：改图工作流的**核心用途（改用户自己的图）完全不可用**。用户只能改内置示例图，且界面没有任何提示。多参 H3 的「参考图/参考视频/参考音频」能力同理全废。

## 缺陷 2

- **严重度**：P1（功能坏）
- **标题**：「取消」只是界面上的假取消 —— 界面立刻说「已取消」，ComfyUI 里任务还在跑
- **复现步骤**：
  1. 任一工作流点「生成」
  2. 出现「取消」按钮后立刻点它
  3. 同时用 `GET http://127.0.0.1:8188/queue` 观察 ComfyUI 队列
- **预期**：取消后 ComfyUI 队列里该任务消失，GPU 停止计算。
- **实际**：
  - 界面：`已提交，等待产出…` → 1.8 秒后 → `已取消`，按钮组从 `[取消, 生成中…]` 变回 `[生成]`（`disabled=false`，可以立刻再提交）
  - **ComfyUI 队列**：点取消前后 `running=1 pending=2` → 取消后仍在跑。我用 `/queue` 的 `delete` + `/interrupt` 手动清理才停
  - 根因（读源码确认）：
    - 前端 `onCancel()` 一进来就 `stopPoll()`，然后 `setJob({ ...job, cancelled: true })` —— 不等后端确认，界面自己宣布取消成功
    - 后端 `cancel()` 发的是 `POST /interrupt`，这是 **ComfyUI 的全局打断**，会打断当前正在跑的任何任务，不只是这一个；且 `/queue delete` 和 `/interrupt` 都是 `.catch(() => {})` 后不检查结果
- **影响**：① 用户以为停了，实际 GPU 还在烧（H3 视频任务一跑就是十几分钟）；② 如果此时有别的任务在跑，会被误杀。

## 缺陷 3

- **严重度**：P1（功能坏）
- **标题**：任务被中断后**永久轮询**，界面永远停在「已提交，等待产出…」，永远看不到失败
- **复现步骤**：
  1. krea2 点「生成」，记下 jobId 与 promptId
  2. 在 ComfyUI 侧把该任务打断（我实测时是用 `POST /interrupt` 清理自己制造的连点任务，正好命中）
  3. 观察界面
- **预期**：AGENTS.md §3.13 ③ 声称已修「生成失败 = 永久轮询」。失败应当出现错误提示。
- **实际**：
  - `GET /comfy-bridge/job/comfy-mvdgcs9u-gfjz5a` 返回：
    ```json
    {"jobId":"comfy-mvdgcs9u-gfjz5a","completed":false,
     "queue":{"running":0,"pending":0}}
    ```
    —— **队列已经空了，任务既不在跑也不在排队，但 `completed` 恒 false、无 `statusStr`**
  - `GET http://127.0.0.1:8188/history/c38e6934-10e3-486b-9da9-4103c4d14103` → `{}`（**ComfyUI 对被打断的任务根本不写 history**）
  - 界面连续 11 秒（12 次采样 × 1.2 s）文字一字不变：`已提交，等待产出… · comfy-mvdgcs9u-gfjz5a`，生成按钮 `disabled=true`，无法重试
  - 截图：`13-A4-permanent-poll.png`
- **根因**：§3.13 ③ 只修了「ComfyUI 写了 history 且 `status_str=error`」这条路。`index.js:181` 的 `if (!h) { return { ...job, completed: false, queue: q } }` 这条分支没有任何终态判定 —— 只要 ComfyUI 不写 history，就永远不终态。
- **影响**：一旦出现（打断 / 崩 / ComfyUI 重启 / 节点报错不写 history），整个工作台卡死，只能刷新页面。

## 缺陷 4

- **严重度**：P1（功能坏）
- **标题**：生成中切到别的 tab 再切回来，**任务状态全丢**，且能重复提交
- **复现步骤**：
  1. 「多参 H3」点生成，等出现「取消」+「已提交，等待产出… · comfy-mvdgu1ew-afj1d2」
  2. 点「轨迹」tab，停 4 秒
  3. 点回「视频工作台」
- **预期**：回来时仍在生成中（至少显示「生成中…」+「取消」）。
- **实际**：
  ```
  before: "已提交，等待产出… · comfy-mvdgu1ew-afj1d2"   hasCancel=true
  after : "资产画布是空的 | 调好参数点「生成」…"          hasCancel=false
          genBtn = [{t:"生成", dis:false}]
  ```
  - 同时 `GET /queue` 显示该任务仍在跑（`running=1`）
  - 用一个自定义提示词标记（`QA-PERSIST-MARKER 自定义提示词`）验过：切走再回来，工作流从「Krea2 生图」被重置成「多参 H3 ★」（order 最小的那个），提示词也被重置成该工作流的默认值
- **影响**：① 用户失去对正在跑的任务的一切控制（没有取消按钮）；② 可以再点生成提交第二份，双倍吃显存（H3 主模型 19.5 GB / 16 GB 卡，直接 OOM 风险）；③ 已调好的参数全丢。

## 缺陷 5

- **严重度**：P1（功能坏）
- **标题**：生成中切换工作流，旧任务**不取消**，变成后端孤儿任务
- **复现步骤**：
  1. krea2 点生成
  2. 1.5 秒后（还在跑）把工作流下拉切到「多参 H3 ★」
- **预期**：切工作流应当取消旧任务，或至少给出提示。
- **实际**：
  - 界面：立刻清空，结果条消失，按钮恢复成「生成」
  - ComfyUI `/history` 里多出**一条 success、2 个产物的记录**（`9157aa9f-f90a-4649-86b5-bc1284bba406`），产物没人认领
  - 连跑 3 次制造了 3 条孤儿：`9157aa9f...` / `ba13570b...` / `61bfe145...`，全部 `client_id=dsh-comfy-bridge`
  - 源码确认：`pickMode()`（`WorkbenchView.js:707-720`）只有 `stopPoll()` + `setJob(null)` + `clearAssets()`，**没有 `bridge.cancel()`**
- **影响**：白白吃显存与时间；产物落在 ComfyUI output 目录里但工作台看不到，用户找不到。

## 缺陷 6

- **严重度**：P1（功能坏）
- **标题**：连续快速点「生成」5 次 → **真的提交 5 个任务**
- **复现步骤**：
  1. 注入 fetch 拦截，记录所有 `/comfy-bridge/generate`
  2. 同步 `click()` 生成按钮 5 次
  3. 查 `GET /queue`
- **预期**：只提交 1 个，其余被 `busy` 挡住。
- **实际**：
  - 拦截到 **5 次** `POST /comfy-bridge/generate`，body 完全相同（`modeId: "yz"`、同一 prompt、同一 steps）
  - ComfyUI `/queue` → `running=1 pending=2`（我随后手动清理了这 5 个我用掉的 yz 任务，`client_id` 全是 `dsh-comfy-bridge`，create_time 集中在 1792305367351~1792305367362，即 11 毫秒内）
  - 根因：`busy` 依赖 `job` state，而 `job` 要等 `await bridge.generate()` 返回后才 `setState` —— 这中间几百毫秒完全没有互斥。
- **影响**：连点 5 次 = 5 份 H3 任务排队，直接吃满 16 GB 卡，后面全部 OOM。用户以为是「点了没反应」。

## 缺陷 7

- **严重度**：P2（体验差）
- **标题**：ComfyUI 未启动时点生成，**界面静默无反应**，14 秒一字不变
- **复现步骤**：
  1. 让 ComfyUI 不运行（我实测时 8188 已被外部停掉，`/comfy-bridge/health` 返回 `{"ok":false,"error":"ComfyUI 未运行或不可达：http://127.0.0.1:8188（fetch failed）"}`）
  2. 点「生成」
  3. 连续观察 14 秒
- **预期**：出现错误提示（如「ComfyUI 未运行」），并引导用户点底部开关启动。
- **实际**：
  - 后端确实返回了可用信息：`POST /comfy-bridge/generate` → `500 {"error":"ComfyUI 未运行或不可达：http://127.0.0.1:8188（fetch failed）","name":"ComfyUnreachable"}`
  - **但界面 12 次采样（间隔 1.2 s，共 14 秒）文字一字不变**：`资产画布是空的 | 调好参数点「生成」…`，无错误条、无 toast、生成按钮仍是可点状态
  - 根因（源码）：`onGenerate` 的 `catch` 确实 `setError(err.message)`，但 `renderResultBar({... error})`（`WorkbenchView.js:1280-1298`）**只在 `modesState === "error"` 时渲染 error**，`modesState === "ok"` 时把 `error` 收进来却从不使用
- **影响**：用户完全不知道发生了什么。最可能的反应是「点了没反应，再点几次」—— 结合缺陷 6，会叠成雪崩。

## 缺陷 10

- **严重度**：P3（瑕疵）
- **标题**：17 个可交互控件里只有 4 个有 tooltip，且内容是 label 复读
- **实测数据**：
  - 有 `title` 的 4 个：`工作流 => 工作流`、`画幅 => 画幅 · 16:9`、`尺寸 => 尺寸 · 1`、`随机种子 => 随机种子`
  - **完全没有 `title` 也没有 `aria-label` 的**：「生成」按钮（`title=""`, `aria-label=null`）、种子输入框（只有 placeholder「留空随机」）
  - `title` 挂在**父 span 而不是按钮本身**的：武打模式开关（按钮 `title=null`，父 span 有 hint）
  - 6 个「增加/减少」箭头按钮 `title=""`
- **影响**：「生成」按钮没有任何 tooltip，快捷键（Ctrl+Enter）没有任何提示；「留空随机」之外的种子行为无说明。武打模式的 hint（那段 4 个 LoRA 的说明）写在父元素上，鼠标停在开关圆点上时**不显示**（浏览器只认 target 自己的 title）。

## 缺陷 11

- **严重度**：P3（瑕疵 · 潜在）
- **标题**：「生成」按钮文字色硬编码 `#fff`，暗色主题下会变白字白底
- **实测数据**：
  - `WorkbenchView.js:1231`：`color: (!modeId || busy) ? "var(--dsw-alias-label-tertiary, #81858c)" : "#fff"`
  - AGENTS.md §3.10 逐字记过这个坑：「必须用 `--dsw-alias-label-primary-foreground` —— 它在浅色下是白、暗色下是黑」
  - 当前 DSH 实例 `colorScheme: light`，扫全部 stylesheet 里 `prefers-color-scheme:dark` / `data-theme` / `.dark` 规则 **0 条** ⇒ DSH 当前没有暗色模式
  - 所以现在是**潜在缺陷**，一旦 DSH 加暗色主题就会炸
- **影响**：现在无影响；属于「已知坑又踩回去」。

# 最该先修的三条

1. **缺陷 2 + 3 + 6**（取消是假的 / 中断后永久轮询 / 连点提交多任务）—— 三条都是「任务状态机」的问题，根都在同一个地方：前端 `job` 状态的终态判定完全依赖 ComfyUI 写 history，而 ComfyUI 有三种情况不写（被打断、被 delete、进程崩）。修法：`job()` 在 `!h` 时**同时查 queue**，若 `running=0 && pending=0` 且 `promptId` 不在 `queue_pending` 里 ⇒ 判定为 `lost` 终态；前端加 `lost` 分支；提交侧加 `submittingRef` 同步锁。
2. **缺陷 1**（改图无上传入口）—— `bind.media` 里声明的槽位一个都没在界面渲染出来。这是「Qwen 改图」这个工作流存在的全部意义所在。
3. **缺陷 4**（切 tab 丢状态）—— 工作台状态全在 React state 里，tab 一卸载就全没。至少要保住「有没有在跑 + jobId」，或者干脆把 job 状态提到插件级别（`apply()` 的闭包里）。
