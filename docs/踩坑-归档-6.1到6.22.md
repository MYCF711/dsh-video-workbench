### 6.3 起进程不弹黑框只能用 VBS

```

   实现见 src/comfy-launcher.mjs 的 launchHidden()

### 6.11 ffmpeg 抽帧：两个必踩的坑（2026-10-18）

```
① ffmpeg 7.x 要求单图输出带 -update 1
   否则报 "does not contain an image sequence pattern or a pattern is invalid
            ... Could not open file"，然后 exit code 非 0，
   看起来像「命令失败」但真正原因藏在 stderr 里。

② -update 1 是【输出选项】，必须放在 -i 之后
   ❌ ffmpeg -y -update 1 -i in.mp4 -frames:v 1 out.png
      → "Error opening input file in.mp4. Error opening input files: Option not found"
      ⚠ 报错行写的是【输入文件打不开】，极容易误判成源文件坏了
   ✅ ffmpeg -y -i in.mp4 -frames:v 1 -update 1 out.png

③ 抽出来的帧不能写 ComfyUI 的 input 目录
   本机 DSH 文件沙箱只允许写工作区：
     C:\Users\Administrator\*.png              → Could not open file（I/O error）
     D:\Comfy-Desktop\ComfyUI-Shared\input\*.png → 同样失败
     D:\主工作区\DSH视频工作台\.frames\*.png     → ✓ 成功
   ⇒ 落盘在工作区，之后走 comfy.uploadImage() 传给 ComfyUI（这条路本来就通）

★ 本机 ffmpeg 位置（PATH 里没有，必须用绝对路径）：
  D:\主工作区\DSH视频工作站\packages\dsh-editor\bin\ffmpeg.exe   v7.1  83.6MB

### 6.17 ComfyUI 对带 Origin 的请求一律 403（2026-10-18）

```
实测（node fetch / curl 双验证）：
  GET http://127.0.0.1:8188/api/view?filename=X&type=output                    → 200
  GET 同上 + Origin: http://127.0.0.1:19499                                    → 403
  OPTIONS 同上（preflight）                                                     → 403

⇒ <img> / <video> 有时带 Origin 有时不带（取决于 CSP / referrer 策略），
  「之前能看」不能当成保证。所有指向 8188 的资源必须走同源代理：

  /comfy-assets/view?filename=X&subfolder=&type=output   （M2 的 lib/index.js 代理）

❌ 实测踩到的症状：画布上 4 张卡全显示「图加载失败（ComfyUI temp 可能已清理）」，
   而同样的文件走代理是 200。
   根因：AssetCanvas.toCards 里 src 用了 bridge.viewUrl(o.url)（直指 8188），
        而 dl 用了 dlUrl(o)（走代理）。一个跨源一个同源，只有显示坏掉。
✅ 修：src 也走 dlUrl(o).replace("&download=1", "")
```

### 6.18 process.cwd() 不可靠 —— 重启会静默丢数据（2026-10-18）

```
❌ const outDir = config.outputDir ?? path.join(process.cwd(), "outputs");

   DSH 由 Start-Process 启动时没指定 -WorkingDirectory，
   所以 process.cwd() 是宿主安装目录，不是项目根。
   ⇒ 存档写到别处，重启后读不到 ⇒ 时间轴变空。

   ★ 这个缺陷特别隐蔽：服务不重启时内存里一切正常，
     只有重启才暴露。我一天重启十几次，每次看到 video(0)
     都以为是「这次没数据」，从没对照磁盘上明明有 4 段。

✅ 修：基于本文件位置推导，与 cwd 无关：
   const HERE_DIR = path.dirname(fileURLToPath(import.meta.url));
   const WORKSPACE_ROOT = path.resolve(HERE_DIR, "..", "..", "..");

   并且【兜旧路径】：按优先级找第一个真的有 timeline-state.json 的目录
     1. 工作区根/outputs
     2. 插件包目录/outputs
     3. process.cwd()/outputs
   否则换路径会让老存档「凭空消失」。

★ 通用纪律：插件里任何「落盘位置」都不能依赖 cwd。
  要么用 import.meta.url 推导，要么让宿主显式配置。
```

### 6.22 反查脚本的删除层有三层，别只看 toggle（2026-10-19）

```
★ 6.21 说「改 delete 前先跑反查」，但反查本身容易做错。
  我在同一份数据上连错两次，都是没把删除层的语义理清。

ComfyUI 里「一个节点会不会被删」有三个来源：

  ① toggle 的 on/off 分支
       bind.toggles.<name>.on.nodes   → 开启时【保留】哪些
       bind.toggles.<name>.off.delete → 关闭时【删除】哪些
  ② always.delete
       永远删，与任何开关无关（本项目：krea2 的 175/176/172）
  ③ 节点的下游连带
       某节点被删 → 它的下游拿不到输入 → ComfyUI 静默跳过（不报错）

⇒ 判断「某节点是否幸存」必须同时看 ①②；
  判断「是否断链」必须再看这个节点在不在 ② 里（在 ② 里就根本不该存在）。

实测踩到的两次错：
  · 先说「176 在 seedvr.off.delete 里」→ 实际不在
  · 再说「176 是假阳性」→ 对，但理由是它在 always.delete 里，
    不是因为它同属 seedvr

★ 已落成工具：packages/dsh-comfy-bridge/tools/check-toggle-deps.mjs
  用法：
    node tools\check-toggle-deps.mjs              # 默认 krea2
    node tools\check-toggle-deps.mjs --verbose    # 打印全部依赖表
  退出码 0 = 全部覆盖，1 = 有未覆盖项。

  它现在正确处理 ①②，跑 krea2 的结果是「✓ 全部 toggle 的依赖都已覆盖」。

★★ 但工具只能筛候选。报出来的每一条，人工还要问：
   1. 这个节点是不是在 always.delete 里？（是 → 根本不该存在，忽略）
   2. 它是不是在别的 toggle 的 off.delete 里？（是 → 两者一起删，不是断链）
   3. 来源节点是不是永不被删？（如 LoadImage 187、一采 VAEDecode 208）

★ 另一个容易搞混的点：**提交成功 ≠ 执行成功**
  实测：二采关+重绘开，修好前修好后提交都返回 {jobId, nodes:18}，
        唯一的区别是执行完 /history 里的 outputs 节点数：
          修好前 [202]
          修好后 [202,186]
  所以验证必须查 /history/<promptId>.outputs 的键，不能只看提交有没有报错。
```
