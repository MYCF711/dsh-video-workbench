### Q1-e · ★★ 整组引用路上的两个「静默失效」bug

两个都是「不报错、看起来正常、只是少了一半」型。值得单独记。

#### ① 自动解绑 effect 把刚绑的槽清掉

```
整组引用往提示词里写的是「@测试组C」（角色名）
但那条「正文删掉 @ 就自动解绑」的 effect 按
  f.displayName || f.name || f.filename（完整文件名）判断：
    text.indexOf("@20261015_160328_QwenEdit_00001_.png") < 0
  ⇒ 判定「用户删了它」⇒ 刚绑的 2 个槽立刻被清空

症状：window.__LAST_GROUP_BIND__.bound 有 2 条（绑定成功）
     但 MediaSlots 一个都不显示
     console 零错误 —— 因为解绑是「正常逻辑」而非异常

修法：绑定记录加 markerName 字段（这组 = 角色名），
     解绑时 `f.markerName || f.displayName || f.name || f.filename`
```

#### ② 连续两次 setFiles，第二次拿到旧 state

```
bindAsset 内部是 setFiles(cur => ({...cur, [slot]: payload}))，
函数式更新本身没问题。但这里连续 await 两次，中间 React 重渲染，
而 applyCharacterGroup 是 useCallback([files]) —— files 一变就换新实例，
正在跑的这个旧实例继续用旧的 filesNow。

症状：bound 有 2 个槽，UI 只显示 1 个

修法：先把所有 payload 取完（无副作用），最后【一次性】setFiles 全写进去
     ⇒ 只有一次 state 更新，不会中途被换掉
```

**共同点与判据**：
```
两者都满足「不报错 + 界面看起来正常 + 结果少了一半」。
这类缺陷只能靠【数一数】发现：
  · 绑了几张？UI 显示几个？（2 vs 0，2 vs 1）
  · 不数就永远发现不了

⇒ 纪律：凡是「批量操作」（绑多张 / 传多项 / 改多处），
  必须断言「输入个数 === 输出个数」，不能只看「有没有成功」。
```

### Q2 · 资产库卡片性能 —— ✅ 已修（虚拟滚动，2026-10-20）

**实测原始问题**：
```
829 张卡 · DOM 29,566 节点 · 每卡两个 select（用途 + 文件夹）
滚动 60 帧：平均 116.1ms/帧 → 9 FPS    p95 230.1ms   max 247.2ms
```
⇒ 不是「可能卡」，是实测确认卡。

**修法**：自写虚拟滚动（不引 react-window）。
```
容器宽度算列数 → 按「行」切片（不按项，否则同行卡片闪烁）
每张卡定高 214px（缩略图 108 + 文本 + 22px 操作行）
只渲染 [firstRow-2, lastRow+2]
上下用空 div 撑高，滚动条长度保持真实
```
配套：optgroup 结构提到模块级 `ROLE_OPTIONS_BY_KIND`；
`RoleSelect`/`FolderSelect` 包 `React.memo`；
`onSaved: () => lib.reload()` → `useCallback` 常量（否则 memo 永远失效）；
容器加 `contain: layout paint style`。

**实测对比**（同一指标）：
```
                    关闭虚拟滚动   开启虚拟滚动    改善
卡片数              829            66            —
DOM 节点           29,566          3,292         -89%
滚动耗时 平均        27.35ms         7.89ms        -71%
         p95       69.60ms        15.60ms       -78%
         max       98.00ms        20.30ms       -79%
```

**★ 方法学教训（值得单独记）**：
```
一开始我用 rAF 帧率测，得到「9 → 16 FPS」，看起来收益很小。
但【纯 rAF 空转的基线只有 27 FPS】—— headless 浏览器本身被节流。
  纯空转        36.6ms/帧 = 27 FPS   ← 环境上限，不是代码问题
  优化前滚动    116.1ms/帧
  优化后滚动     62.5ms/帧

⇒ 只看绝对 FPS 会得出「优化没用」的错误结论。
  改用同步 performance.now() 量「滚动引起的脚本+布局耗时」，
  排除 rAF 的 16.6ms 节流底线，才拿到真实的 27.35 → 7.89ms。

★★ 通用纪律：在 headless / 远程 / 虚拟化环境里做性能测量，
   必须先量一条「什么都不做」的基线。否则会把环境上限当成代码问题，
   或者反过来把真实改善看成没改善。
```

**功能回归**：
```
顶部：32 张卡 · 三个分组标题都在
中间：66 张卡 · 上传按钮 / ＋文件夹按钮都在
```

### 踩到的 5 个坑（按发现顺序）

#### ① `/plugin-assets/**` 全 404

```
/plugin-assets/dsh-artcraft-tab/assets/artcraft.js  → 404
/plugin-assets/dsh-comfy-workbench-tab/package.json → 404
/plugin-assets/<任意插件>/任意文件                    → 404
```

这个 DSH 版本**没有把插件目录暴露成静态资源**，只暴露 `package.json`
声明的 main / client 入口。

**修**：ArtCraft 的 8MB 产物作为字符串常量内联进 client.js，
运行时 `new Function` 求值。代价是 client.js 8.5MB，
收益是能在真实 DSH 里跑起来。

#### ② `ReferenceError: require is not defined`

ArtCraft 产物里保留了 `require("react")`（打包时 react 设成 external）。
`new Function` 的作用域没有 require。

**修**：把宿主 IIFE factory 的 require 一路透传到组件，
求值时作为参数传入。

#### ③ React 把 ArtCraft 的 DOM 清掉了 ← 最隐蔽

诊断轨迹是决定性证据：
```
just-mounted  childCount=0   htmlLen=11
t+100         childCount=1   htmlLen=3136     ← 渲染中
t+300         childCount=1   htmlLen=64415    ← 完整渲染
t+1000        childCount=0   htmlLen=0        ← 被清空！
```

根因：我给容器渲染了「正在载入…」文本，`setState` 后
React 认为子节点该从 `[文本]` 变成 `[]`，
**顺手把 ArtCraft 塞进去的 64KB DOM 一起清了**。

**这是 React 的一条铁律**：凡是第三方库用命令式 API 接管的容器，
React 不能再往里渲染任何 children。

**修**：容器完全空着给 ArtCraft 独占，加载提示放到兄弟节点。

#### ④ `scene.tracks.overlay is not iterable`

```js
// 我以为是（错的）
tracks: { video: [...], audio: [...] }

// 实际是
tracks: {
  overlay: [],       // 叠加轨数组
  main: { ... },     // ← 单个对象，键名是 main 不是 video
  audio: [],         // 音频轨数组
}
```

**教训**：`video` 和 `audio` 都是轨道，很容易想当然认为形状一样。
实际是 **main 单数、audio 复数**。
得看 ArtCraft 自己的 `buildDefaultScene` 怎么造，不能类比。

#### ⑤ `/comfy-assets/library` 的 offset 从来没实现过 ← 后端真 bug

```
实测：offset=0/500/1000/1500 四次返回完全相同的内容
根因：只做了 items.slice(0, limit)，从没读 offset
后果：选择器循环 20 次拿到 10000 条重复
      界面显示「可选择 10000 项」（真实 857）
      浏览器同时发 10000 个图片请求，大量 img 变成破图
修：slice(offset, offset + limit)

修复后：offset=0→500条 / offset=500→357条 / offset=800→57条
        500 + 357 = 857 ✓
```

### 这一轮修的 6 个 bug（全部是「静默失效」类）

#### ① `MediaTime` 类型搞错整整一轮

```ts
// video-editor/src/lib/wasm/media-time.ts 逐字
// Integer-tick time. Mirrors MediaTime(i64)
export type MediaTime = number & { readonly __mediaTime: unique symbol };
export const TICKS_PER_SECOND = _TICKS_PER_SECOND();     // 实测 = 120000
```

**`MediaTime` 是整数 tick，不是 `{numerator, denominator}`。** 那个是 `FrameRate` 的类型。
传对象进去 → `addMediaTime` 里 `a + b` 变成 `"[object Object][object Object]"` → 报错。

#### ② esbuild 的导出被 payload 劫持

ArtCraft 的 8MB 源码里有 `module.exports = __toCommonJS(...)`。
**esbuild 不区分内容是否在字符串里**，把它当成本模块的导出声明：

```
导出变成：{ mount, toProject, unmount }    ← ArtCraft 的
应该是：  { apply, inject, name }          ← 我的
⇒ DSH 拿不到 apply ⇒ 插件静默不激活 ⇒ tab 在但内容空白
```

修法：payload 改成 **base64**（只含字母数字，esbuild 扫不到代码特征）。

#### ③ `createTrimWriter` 没 import

加了 `onSave: createTrimWriter(...)` 但漏了 import → `ReferenceError`。

#### ④ 主题轮询触发 React #300

```js
React.useEffect(() => {
  const stop = watchDshTheme(null, cb);   // 每 1 秒 getComputedStyle
  return stop;
}, []);
```

在提交阶段读布局样式会触发强制同步布局，打断 React 提交
→ `Rendered more hooks than during the previous render`。

修法：延迟 1.5 秒启动 + 间隔放宽到 2 秒 + 卸载时清定时器。

#### ⑤ 资产必须先注册，不能只靠 adapter

```js
// timeline-element.tsx:1096 逐字
const mediaAssets = useEditor((e) => e.media.getAssets());
const mediaAsset = mediaAssets.find((a) => a.id === element.mediaId);
```

**ArtCraft 不做按需 `resolveMedia`，而是先查「已注册的资产表」。** 表里没有就静默不渲染。
加日志确认过：`resolveMedia` 被调用 **0 次**。

#### ⑥ `clip.kind` 不是媒体类型

```js
// 错
const kind = clip.kind === "audio" ? "audio" : (clip.kind === "image" ? "image" : "video");
```

`clip.kind` 表示**在哪条轨上**。实测那个 clip 在视频轨（`kind="video"`），
但 `rendered.filename` 是 `.png` → 判成 `type:"video"` → ArtCraft 用 `<video>` 加载 PNG → 静默失败。

改成按**实际扩展名**判断。

#### ⑦ `duration` 语义搞错（导致 trim 改了但没用）

```js
// 错：duration = out - in（源素材全长）
// 对：duration = trimEnd - trimStart（时间轴上占多长）
```

只改 `trim` 但 `duration` 恒等于全长 → **界面毫无变化、导出仍按全长**。

#### ⑧ `Copy-Item` 把修复覆盖回去

修好了 ArtCraft 侧的 `tracks.overlay`，同步时用 `Copy-Item` 把工作台那份**旧的**覆盖了过去
→ `scene.tracks.overlay is not iterable` 回归。

**纪律：两份文件（工作台 `timeline-projection.mjs` / ArtCraft `dsh-projection.ts`）
必须同时修，单向覆盖前先确认哪份是新的。**

```
时间轴: clip1.x=406 w=121 / clip2.x=530 w=245  → 首尾相接（406+121≈527）
总时长: 00:00:04:12 = 4.5 秒
导出:   Duration: 00:00:04.50   ← ffmpeg 实测，1.5+3=4.5 ✓
```

### 这一轮又修的 bug

#### ⑨ `startTime` 累加用错了量（双 clip 才暴露）

```js
// 错：t += dur   （dur = out - in = 源素材全长 5 秒）
// 对：t += timeToSec(el.duration)   （已按 trim 算成 1.5 秒）
```

**症状**：两个 clip 之间出现 3.5 秒空隙，总时长 8 秒（应为 6.5）。

**根因**：`el.duration` 已按 trim 计算，而游标仍按 `out - in` 前进。
**为什么单 clip 时没发现**：只有一个 clip 时没有「下一个 clip 的位置」，
空隙不可见，直到加了第二个才暴露。

★ 教训：**位置相关的 bug 需要 ≥2 个元素才能暴露。**
单元素测试对「布局/偏移/累加」这类缺陷是盲的。

#### ⑩ 视频缺元数据导致时间轴条带空白

补 `probeMeta()`：用 `<video preload="metadata">` 解码一次拿 duration/宽高。

```
实测: duration 2.333333（与 ffprobe 的 00:00:02.33 一致）
      width 1664  height 928
```

★ 注意 `muted = true` 与 `playsInline = true` 必须设 ——
某些浏览器对带音轨的 video 会拒绝在后台加载元数据。

## 十 · 音频轨 + 音视频合成（2026-10-21 凌晨）

### 终验：导出文件有双流

```
Duration: 00:00:08.01
Stream #0:0  Video: h264 (High) avc1  1920×1080  24fps  1406 kb/s
Stream #0:1  Audio: aac (LC) mp4a  44100 Hz stereo  191 kb/s
文件: 1564.7KB
```

**对比修复前**：1375.1KB，只有 `Stream #0:0 Video` —— 音频被静默丢弃。

### 这轮修的 2 个 bug

#### ⑬ `mediaId` 猜错前缀（只在音频上暴露）

```
资产表真实 id = "editor:<WORKSPACE>\资产库\音频\test-mix.m4a"
投影猜出来的   = "output:test-mix.m4a"        ← 不存在
```

**根因**：投影是纯函数，拿不到资产表，只能靠「src 是否绝对路径」猜前缀。
而音频资产的 `src` 是 `editor`（来源标签），不是 `output`。

**视频恰好猜对了**，因为它们的 src 就是 output。
⇒ 这个 bug 只在音频（或任何非 output/input 来源的资产）上暴露。

**修法**：在能拿到资产表的地方（client.js）按文件名把 mediaId 修正成真实 id。
新增 `fixupMediaIds(project, libraryItems)`。

#### ⑭ `AudioElement` 是联合类型，必须声明 sourceType

```ts
// video-editor/src/lib/timeline/types.ts 逐字
export type AudioElement = UploadAudioElement | LibraryAudioElement;

UploadAudioElement   { type:"audio", sourceType:"upload",  mediaId }
LibraryAudioElement  { type:"audio", sourceType:"library", sourceUrl }
```

我两个都没设，于是合成代码走：
```js
if (element.sourceType === "upload") { … }      // 不进（undefined）
if (element.buffer) return element.buffer;       // 不进（没预解码）
const response = await fetch(element.sourceUrl); // ← fetch(undefined)
```
`fetch(undefined)` 抛错 → catch 里 warn → 返回 null → 音频被丢弃。
而 `createTimelineAudioBuffer` 见 `audioElements.length === 0` 就返回 null
⇒ 导出只有视频流。

**症状极隐蔽**：时间轴上音频条带**正常显示**（另一条渲染路径），
只有导出文件里少音频流，光看界面看不出来。

**修法**：`element.sourceType = "upload"`（我们已有媒体注册，走资产表那条路）。

### 规律：不能用「视频能跑」推断「音频也能跑」

累计 14 个 bug 里，有 4 个（⑤⑥⑬⑭）是「视频通过但音频失败」：

```
⑤ 资产必须先注册（resolveMedia 0 次调用）    —— 视频音频都受影响，但先被视频暴露
⑥ clip.kind 不是媒体类型                      —— 图片被当视频
⑬ mediaId 前缀猜错                            —— 只有音频暴露
⑭ sourceType 没设                             —— 只有音频暴露
```

**为什么音频更容易漏**：
· 音频没有视觉产物 —— 条带能画出来就以为对了
· 音频的资产 id 格式和视频不同（editor: vs output:）
· 音频的 element 是联合类型，视频不是
· 音频的影响只在导出时体现，不像视频那样预览就能看出

★ 纪律：**加一种媒体类型，就要独立验它的完整链路**，
不要假设「和上一种差不多」。

## 十四 · 验收自检扩充到 13 条 + 找出两处真缺口（2026-10-21）

### 一 · 自检工具自身的第一个教训：变异必须改「行为」

我最初给 `firstFreeSlotFor` 写的变异是：
```js
find:    "export function firstFreeSlotFor(media, files, kind) {"
replace: "... { return null;"
```

注入后：
```js
export function firstFreeSlotFor(media, files, kind) { return null;
  for (const [slot, spec] of Object.entries(media ?? {})) { ... }   ← 死代码
  return null;
}
```

**语法合法、行为确实坏了（永远返回 null），但验收仍然 54/54 通过。**

原因：我的源码断言验的是「源码里有 `Object.entries(media)`」——
那行还在，只是永不执行。

⇒ **源码层断言对语义变异天然无力。** 它能验「代码写得对不对」，
不能验「跑起来对不对」。

**改成两条真正的语义变异**（改动循环内部的条件，不产生死代码）之后就抓住了：
```js
// 变异 A：kind 过滤失效
find:    "if (spec?.kind && spec.kind !== kind) continue;"
replace: "if (false) continue;"
// ⇒ @ 引用音频会被塞进图片槽

// 变异 B：忽略槽是否已占用
find:    "if (!files?.[slot]) return { slot, ... };"
replace: "return { slot, ... };"
// ⇒ 第二个 @ 引用的图会覆盖第一个
```

### 二 · 它找出了一个真实的功能盲区

`firstFreeSlotFor`（决定 @ 引用的图绑到哪个槽）**此前完全没有被验收覆盖**。

如果它坏了，表现是：
```

用户看到引用成功了，模型没收到那张图
```

```

  ✅ firstFreeSlotFor 存在
  ✅ 它遍历了 media 条目
  ✅ 它在遍历里返回 { slot, ... }（而不是直接 null）
  ✅ 只有遍历完才 return null
  ✅ 按 spec.kind 过滤不匹配的槽

  ✅ 全部占满时返回 null（不是抛错）
```

```
1. 写断言之后，问「把被测改坏它会红吗」。不会红就是没写。
2. 变异要改【行为】，不能只是制造死代码 —— 源码断言抓不住语义变异。
3. 源码层断言的边界：它能验「代码写得对不对」，
   不能验「跑起来对不对」。语义正确性必须靠纯逻辑复刻或真实调用。
```

## 十六 · 任务书与现实的三处偏离（如实记录）

### 偏离 1 · 任务书三-1「新会话时由 LLM 判断项目归属并询问用户」


**⇒ 两侧都拿不到 LLM。**

**实际做法**（`AssetLibrary.js:2004` 有注释）：

```
理由写在代码里：「让用户在入库那一刻直接填，比「模型猜 → 用户再确认」少一步」
```

### 三 · 正确的调用方式（踩了三个坑才找到）

```
❌ prepareCall()                      → Cannot read properties of undefined (reading 'provider')
❌ prepareCall({provider})            → adapter returned invalid exact model metadata
❌ call.stream(任何参数)              → "prepared LLM call config changed before adapter dispatch"
   试过 8 种形状全报这个错：
     {prompt} / {input} / {text} / {content} / {messages:[...]}
     {system,prompt} / {systemPrompt,prompt} / [{role,content}]
   ⇒ call.stream 是【低层】函数，config 已固定，不能再传消息

✅ llm.stream({ provider, model, messages })
   高层接口，一次搞定，不需要 prepareCall
   messages 的 content 必须是【块数组】：
     ❌ { role:"user", content:"文字" }        → content.some is not a function
     ✅ { role:"user", content:[{type:"text", text:"文字"}] }
```

### 四 · 为什么最终还是不通（三个 provider 各自的死因）

```
  ⇒ 本地中转服务根本没起来。报 "Connection error."

deepseek-official / deepseek-account
  → 不在 profile 的 cordis.patch.yml 里（只有 zcode-free 是显式配置的）
```
