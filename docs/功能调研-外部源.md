## 一 · 图/视频生成工作流

### F1. 角色卡：资产库里的「定妆图组」自动注入参考图槽位

- **解决什么问题**：同一个角色跨镜头变脸。现在 yz 有 6 个参考图槽位，但每生成一段都要人工重新挑图、重新写 `<Subject 1>` 指向第几张；换一段就忘。角色一多必乱。
- **来源**：
  - ComfyUI 官方 Examples 索引（角色/风格一致性被列为独立主题）：<https://comfyanonymous.github.io/ComfyUI_examples/>
  - B站《【ComfyUI】最强AI视频人物一致性解决方案》：<https://www.bilibili.com/video/BV1ezU6BZEtt/>
  - 知乎《ComfyUI 短剧工作流合集：从角色设计到视频生成》—— 把一致性拆成六步管线，第一步就是角色定妆：<https://zhuanlan.zhihu.com/p/2063707470401365950>
  - `smart-comfyui-gallery` **392 star**（按 prompt/model/LoRA/date/comment 过滤、状态标签、评分、虚拟合集）：<https://github.com/biagiomaf/smart-comfyui-gallery>
  - `Image-MetaHub` **333 star**（按提示词/metadata/视觉相似度检索生成结果）：<https://github.com/LuqP2/Image-MetaHub>
- **怎么实现**（全部在现有工作台内）：
  1. 素材库 `assets.mjs` 现有字段够用（`hash` / `tags` / `group`），加一个约定：`tags` 里含 `role:character` + `group:<角色名>` 的资产即「定妆图组」。
  2. `add_shots` 增加可选参数 `characters: ["角色A", "角色B"]`；host 侧按顺序取该角色的定妆图，填进 `ref_image_0..N`（bind 已有 6 槽，够 2~3 角色 + 场景图）。
  3. 提示词侧由 F12 的模板生成 `<Subject 1> is the character in <Picture 1>` —— 这句话格式与本机 `yz.bind.json` 的默认 prompt 逐字一致，不需要新模型。
  4. 生成结果自动回填该角色的 `group`，下次同类镜头直接复用。
- **工作量**：**中**（素材库打标约定 + `add_shots` 参数 + host 槽位注入 + 提示词拼接，估 400~500 行，含 verify）
- **优先级**：**P0** —— 一致性是 AI 短剧第一痛点，而槽位和资产库都已经在了，缺的只是「记住谁是谁」。

### F2. 首尾帧续接：上一段的末帧当下一段的首帧

- **解决什么问题**：镜头之间没有物理连续性。现在两段视频各自独立生成，接在一起人物位置/光向/景别全变，观众一眼看出是拼的。
- **来源**：
  - ComfyUI 官方模板《Wan2.1 VACE 首尾帧》—— 明确了端点锚定的做法与两条硬约束：**尺寸需为 16 的倍数，总帧数需满足 (Length−1) 能被 4 整除**：<https://comfy.org/zh/workflows/video_wan_vace_flf2v-45c0ce6bcf2e/>
  - RunningHub《KJ版混元首尾帧强一致性图生视频追色工作流》：<https://www.runninghub.ai/zh-tw/post/1898786623557947394>
  - RunningHub《WAN2.2-首尾帧视频工作流》：<https://www.runninghub.ai/zh-tw/post/1981935370910744577>
- **怎么实现**：
  1. 本机 `MiniMaxH3ImageToVideo` **支持** `first_frame` / `last_frame`（object_info 实测），但当前 yz 链路用的是 `ReferenceToVideo`（读 `yz-ultimate-full.json` 确认无 ImageToVideo 节点）⇒ 需要**新增一条 fl2v bind**，不是改造现有 yz。
  2. 时间轴「上一段末帧 → 下一段首帧」：用已有 ffmpeg 能力抽末帧（`-sseof` 或 `extract-frame`），落进素材库，作为下一段 `first_frame`。
  3. 衔接校验不靠肉眼：对末帧/首帧做 `ssim` 比对（见 F10），低于阈值就明确报「这一段接不上」，而不是让主人自己看。
  4. 帧数网格要分开处理：H3 是 **17k+5 且偶数**（`length.mjs` 已实现吸附），Wan VACE 是 4n+1 —— 两套网格别混用，bind 里按 modeId 分派。
- **工作量**：**大**（多一条工作流 + 首尾帧抽取与回填 + 网格校验 + 真跑验收，估 800~1200 行）
- **优先级**：**P1** —— 方案书 §二 曾把「首尾帧衔接（mean_abs_diff<10）」列为非目标并排在 M4；这是补那一笔，但要先有 F10 的质检口径才谈得上「<10」。

### F3. N 选 1：一条分镜出多条候选 + 参数矩阵对照

- **解决什么问题**：VHS 时代的「抽卡」—— 一条分镜只出 1 条，不满意只能整条重跑，好坏全凭运气且没有并排可比的界面。
- **来源**：
  - ComfyUI 官方模板《Prompt Multi Batch Generation》（`FL_PromptMulti`，一次队列塞多个提示词并排比）：<https://comfy.org/workflows/templates_purz_batch_generation-c51538d3e644/>
  - **bytedance/comfyui-lumi-batcher 650 star**（GPL-3.0）—— 任意工作流参数自由交叉测试、参数组自由组合、**多维网格预览 + 批量导出**：<https://github.com/bytedance/comfyui-lumi-batcher>
- **怎么实现**：
  1. 现状：krea2 有 `batch`（张数）变量，yz **没有** batch 概念。
  2. 时间轴层加「候选」概念：一条 shot 下挂 N 个 candidate（各自的 seed / 产物 / 时长），只有一个被「当选」进时间轴。数据落在现有 `host-store.mjs`，不新建 store。
  3. Agent 侧加 `timeline_candidates {clipId, n, varyBy: "seed"|"steps"|"prompt"}`；宿主按 varyBy 只改一个维度，避免「批量」变成「盲抽」。
  4. UI：并排网格 + 一键当选（照 lumi-batcher 的多维网格，而不是简单列表）。
- **工作量**：**中**（store 扩字段 + 生成编排 + 选择 UI，估 600~800 行）
- **优先级**：**P1** —— 它同时是 F7「审片台」的前置数据层。

### F4. 出片增强链：补帧 + 视频级 SeedVR2 放大

- **解决什么问题**：H3 只出 24fps、124~362 帧；导入时间轴拼成片后，镜头运动明显发顿、放大后细节糊。现在链路上只有 **图片** 的 SeedVR2 放大，视频没有。
- **来源**：
  - `FrameInterpolate` 节点（本机 object_info 实测存在，输入 `interp_model, images, multiplier`）；`length.mjs` 注释已写明「RIFE/FILM 常规 2x/4x，奇数会出半帧」⇒ 主人本来就打算补帧，只是网格吸附做了、补帧没做
  - ComfyUI 官方模板《SeedVR2：视频放大》（`seedvr2_videoupscaler`）：<https://comfy.org/zh/workflows/utility_seedvr2_video_upscale-aac8b0d80e73/>
  - ComfyUI 官方模板《SeedVR2：图像放大》（本机 krea2 已在用的一支）：<https://comfy.org/zh/workflows/utility_seedvr2_image_upscale-857e50707831/>
- **怎么实现**：
  1. 新增一条 `upscale` bind：`VHS_LoadVideo` → `SeedVR2Preprocess` → `SeedVR2TemporalChunk` → `SeedVR2TemporalMerge`（4 个节点本机已装）→ `VHS_VideoCombine`。
  2. 补帧：`FrameInterpolate(multiplier=2)` 与 SeedVR2 串在一条链路里，避免「先放大再补帧」的二次编码损失。
  3. 作为时间轴的**段级操作**（`timeline_edit_clip {op:"enhance"}`），和已有 `speed/crop/trim` 同一入口，不新增界面。
- **工作量**：**中**（多 2 条 bind + 段级操作 + 真跑；`interp_model` 具体用哪个模型**未验证**，本机模型清单未查——8188 末段不可达）
- **优先级**：**P2** —— 收益明显但可以用 ffmpeg 的 `minterpolate` 先顶着（质量差但零模型依赖）。

## 二 · Agent 与人协同的交互模式

### F5. 把「闸门」从提示词扩到参数：谁该拍板写在代码里

- **解决什么问题**：Agent 现在被 `prompt-gate.mjs` 管住了提示词，但**时长、步数、种子、画幅**它仍可随手改 —— 而这三样直接决定成本和成片节奏。人也不知道哪些值是自己定的、哪些是 Agent 改的。
- **来源**：
  - 本机 `dsh-editor/src/prompt-gate.mjs` 已实现的三层强制（规则内嵌 / 改提示词必须过闸门 / 生成前复查）—— 这是全项目里最值得复制的模式
  - `mikehalleen/the-halleen-machine` **19 star**（AGPL-3.0）—— 「Agent 驱动 + 项目时间轴 + 可复用素材库（姿势/角色/地点/风格）+ 批量生成/放大/导出」，与本项目架构最像的外部样本，且它明确把「vision QC、prompt revision」做成了 Agent 侧动作：<https://github.com/mikehalleen/the-halleen-machine>
- **怎么实现**：
  1. 把 `prompt-gate.mjs` 的守卫泛化成一张**字段权限表**：`durationSec` / `steps` / `seed` / `aspect` 标为 `user-owned`，Agent 只能「建议」不能「直改」；改必须带 `reason`，并记进已有的 `history`（本来就有 `who: agent|user`）。
  2. 用户手点 UI 完全不受限（沿用现有豁免：`who === "user"` 直接放行）。
  3. 工具返回里附「当前参数是谁定的」—— 和现有 `buildPromptRequirements()` 内嵌规则摘要同一个做法。
- **工作量**：**小**（改 `prompt-gate.mjs` + 1 张表 + 断言，估 150~250 行）
- **优先级**：**P1** —— 成本极低，但把「Agent 会乱改」从口头约定变成结构约束。

### F6. 人先粗排、Agent 精修：分镜表交接协议

- **解决什么问题**：现在只有「Agent 一把梭」和「人全手搓」两个极端。真实创作是：人定要几个镜头、每镜说什么、多长；Agent 负责把它写成合规的 H3 结构化提示词。
- **来源**：
  - `ATH-MaaS/Pixelle-Video` **29128 star**（Apache-2.0）—— 全自动短视频引擎，流程是「AI 写稿 → 配图规划 → 逐句处理 → 视频合成」，**每一环都支持人干预 + 可选不同 AI 模型**，且明确允许「固定文案内容」直接生成（即人先给死稿，AI 只做执行）：<https://github.com/ATH-MaaS/Pixelle-Video>
  - 本机 `prompt-gate.mjs` 的三层强制，本身就是「人定规则、Agent 填内容」的雏形
- **怎么实现**：
  1. `timeline_add_shots` 允许 `prompt` 为空、只给 `{台词, durationSec, 画面意图}` —— 落成「草稿态 shot」，UI 上用灰色占位显示。
  2. 新增 `timeline_draft_plan {clipIds}`：Agent 只为草稿态 shot 补结构化提示词，**不碰时长与顺序**（那是人的活）。
  3. 草稿态 shot 禁止 `timeline_generate`（沿用闸门里已有的拒绝机制），必须先被精修过。
  4. 谁改了哪一格，`history` 里本来就分 `who`——UI 上加一列「定稿人」即可。
- **工作量**：**小~中**（`add_shots` 放宽 + 1 个工具 + 草稿态渲染，估 250~400 行）
- **优先级**：**P0** —— 这是「人机协同」真正落地的那一格，而不是口号。

### F7. 候选审片台：Agent 生成、人挑选、Agent 只改被否的那条

- **解决什么问题**：现在「重跑」是全量重跑。人看完不满意，说一句「换」，Agent 就整条重来 —— 好的部分也一起丢了。人真正想说的是「这一条不行，但要保留第 2 段的光」。
- **来源**：
  - `bytedance/comfyui-lumi-batcher` 的多维网格预览（把参数轴 × 结果放成网格，直接对比挑）：<https://github.com/bytedance/comfyui-lumi-batcher>
  - `smart-comfyui-gallery` **392 star** 的状态标签 + 评分 + 虚拟合集（对结果做取舍分类，而不是只按文件名堆着）：<https://github.com/biagiomaf/smart-comfyui-gallery>
  - `Pixelle-Video` 的「预览模板 / 换 BGM」人机分工点（人只在关键拍板处介入）：<https://github.com/ATH-MaaS/Pixelle-Video>
- **怎么实现**：
  1. 数据层直接用 F3 的 candidate 结构。
  2. 人要能表达三种否决：`重出 / 只改提示词 / 只改某一参数`。UI 上三个按钮，分别落到 `timeline_generate`（重出）、`timeline_update_shot`（改词，走闸门）、`timeline_edit_clip`（改参数）。
  3. Agent 侧收 `timeline_review {clipId, verdict, keep: ["光","构图"], drop: ["动作"]}` —— 把人的偏好结构化，而不是转成一句自然语言丢掉。
  4. 落选候选不删（哈希去重已在，存着不贵），否则下次从零再抽。
- **工作量**：**中**（依赖 F3；审片 UI + review 工具 + 落选留存，估 400~600 行）
- **优先级**：**P2**

## 三 · 时间轴/剪辑

### F8. 段间转场：xfade（本机 ffmpeg 已支持 57 种）

- **解决什么问题**：现在拼片是硬切（`render.mjs` 里 grep `xfade` 零命中，只有 `concat`）。硬切的每一处接缝都在提醒观众「这是拼的」，尤其 AI 生成的两段画面本来就不连续。
- **来源**：
  - FFmpeg 官方 Xfade 文档（含 57 种 transition 与 offset 计算公式）：<https://trac.ffmpeg.org/wiki/Xfade>
  - 本机实测 `ffmpeg -h filter=xfade` 列出 `fade / wipeleft / slideleft / circleopen / dissolve / pixelize / zoomin / coverleft / revealright …` 共 57 项（transition 取值 0~57）
- **怎么实现**：
  1. 改 `dsh-editor/src/render.mjs`：现在是把每段归一后用 `concat` 串起来；改成可选的「相邻两段 `xfade` 链」。
  2. 关键算式（官方 wiki 的口径）：第 i 处 `offset = 累计已播时长 − transition_duration`；转场会让总时长**缩短** `(n−1) × duration`，`expectedDuration` 要同步修正，否则现有的时长断言会误判。
  3. 音频侧必须同步 `acrossfade`，否则音画在接缝处错位 —— 这条是 `AGENTS.md §3.2` 里已经踩过的同类坑（concat 必须 `asetpts`）。
  4. 时间轴上给「接缝」一个默认值（例如 `dissolve 0.3s`），段级可覆盖。
- **工作量**：**小**（只改 `render.mjs` 一条 filtergraph 分支 + 时长断言修正 + verify，估 200~300 行）
- **优先级**：**P0** —— 投入产出比全清单最高：本机 ffmpeg 已就绪、零模型依赖、改一个文件。

### F9. 字幕：faster-whisper 出 SRT → 烧入

- **解决什么问题**：H3 生成的视频**自带音轨**（`yz-result.mp4` = aac 32000Hz stereo），但成片**完全没有字幕**。AI 短剧没有字幕 = 不能发布。而角色说什么只有提示词里知道，成片里听不清。
- **来源**：
  - 本机实测：`faster_whisper` **1.2.1 可 import**；ffmpeg 7.1 有 `subtitles` / `ass` / `drawtext` 滤镜；中文字体 `msyh.ttc` / `NotoSansSC-VF.ttf` / `simhei.ttf` 齐备
  - 本机 ffmpeg **没有** `whisper` 滤镜（`-filters | grep whisper` 实测为空）⇒ 不能纯 ffmpeg 出字幕，必须走 Python 子进程
  - 参考实现（faster-whisper 提取音频生成 srt/ass）：<https://github.com/lissettecarlr/auto-subtitle>
- **怎么实现**：
  1. host 侧新增 `subtitle.mjs`：`ffmpeg 抽音轨 → 子进程跑 faster_whisper → 出 SRT → ffmpeg subtitles 烧入 / 或导出 .srt 软字幕`。
  2. 模型：`D:\主工作区\models--Systran--faster-whisper-small` **是空目录**（实测），首次需下载 small（约 500MB）；或用 `compute_type=int8` 在 CPU 上跑，避免和 ComfyUI 抢显存 —— **这条很重要**：H3 主模型 19.5GB，RTX 5070 Ti 只有 16GB（`AGENTS.md §3.8`），字幕任务绝不能用 GPU。
  3. 提示词里已有台词（`prompt-gate.mjs` 甚至在校验「台词字数 ÷ 4.5 字/秒 ≥ 时长」）⇒ 优先用已知台词对齐时间轴，whisper 只做时间戳校正。这比纯 ASR 准得多。
  4. 工具：`timeline_subtitle {clipIds, mode: "burn"|"srt", style}`；烧入用 `subtitles` 滤镜 + `force_style` 指定 `msyh`。
- **工作量**：**中**（子进程封装 + 时间戳对齐 + 烧入 + 首次模型下载，估 400~600 行）
- **优先级**：**P0** —— 依赖全在本机、零云端、缺口 100%。

### F10. 衔接质检：末帧/首帧 SSIM + 黑帧/卡帧自动检测

- **解决什么问题**：一条 5 秒的视频 95 秒才出（`yz` 实测）。人不可能逐段逐帧检查「上一段结尾和下一段开头接不接得上」「中间有没有糊成一片或卡住」。现在的 `audit_audio` 只管声音，画面完全没人管。
- **来源**：
  - 本机 ffmpeg 实测可用：`ssim` / `psnr`（两路视频相似度）、`freezedetect`（卡帧）、`blackdetect`（黑场）、`signalstats`（逐帧统计）
  - `the-halleen-machine` 明确把「vision QC」列为 Agent 侧动作（批量生成→自动质检→人工只处理被标记的）：<https://github.com/mikehalleen/the-halleen-machine>
  - 方案书 `docs/方案-DSH视频工作台.md` §二 已把「首尾帧衔接（mean_abs_diff<10）」写成验收口径 —— 这套质检正是把那个口径变成可执行的东西
- **怎么实现**：
  1. 新增 `timeline_audit_cuts {clipIds}`：
     - 相邻两段：抽 A 末帧 + B 首帧 → `ssim` 比对 → 低于阈值（建议 0.6，**需实测标定**）报「接不上」；
     - 单段内部：`freezedetect=n=-60dB:d=0.5` 查卡帧、`blackdetect` 查黑场。
  2. 复用已有 `ffmpeg-resolver.mjs` 找 ffmpeg，不新增依赖。
  3. 结果落到 UI 的接缝标记上（时间轴上直接画红点），Agent 也能读 —— 与 `audit_audio` 对称，命名与返回结构保持一致。
  4. 判据要**实测标定**，不能凭空写 0.6：先拿现有 `docs\evidence\yz-result.mp4` 与 `krea2-result.png` 跑一遍拿到基线分布。
- **工作量**：**小**（1 个 host 模块 + 1 个工具 + 时间轴标记，估 250~350 行）
- **优先级**：**P0** —— 纯 ffmpeg、零模型、和已有 `audit_audio` 同构，且它让「重跑」有了依据（哪一段该重跑是算出来的，不是猜的）。

### F11.（可选，依赖外部模型）口型同步：Wan2.2-S2V 音频驱动

- **解决什么问题**：H3 自带音频，但口型与台词常常对不上；若走 TTS 配音（本机无 TTS，M8 已确认是「编辑已有音频」），口型必然错位。
- **来源**：ComfyUI 官方模板《Wan2.2-S2V 音频驱动视频生成》：<https://comfy.org/zh/workflows/video_wan2_2_14B_s2v-02b3722db38c/>（官方文档：<https://docs.comfy.org/zh/tutorials/video/wan/wan2-2-s2v>）
- **怎么实现**：需要 `wan2.2_s2v_14B` + `wav2vec2_large_english_fp16` 音频编码器 + `wan_2.1_vae`；新一条 bind，输入「参考图 + 音频」。**本机是否已装这些模型：未验证**（8188 末段不可达）。
- **工作量**：**大**
- **优先级**：**P2** —— 先把 F9 字幕做出来，口型问题就退化成「观众看得懂 vs 对得上口型」的次要问题。

## 四 · 提示词工程的实用工具

### F12. 提示词库 + Recipe：把提示词和它当时的参数一起存

- **解决什么问题**：现在提示词是「一次性输入框」。满意的结果想复现，得手动抄回提示词、记得住当时是 8 步还是 10 步、挂了哪个开关、用了哪几张参考图 —— 抄漏一样结果就不同。
- **来源**：
  - `FranckyB/ComfyUI-Prompt-Manager` **167 star** —— 核心设计正是 **Recipe**：提示词 + **LoRA stack** 一起保存，还能从图片/视频 metadata 里反抽提示词：<https://github.com/FranckyB/ComfyUI-Prompt-Manager>
  - `ComfyAssets/ComfyUI_PromptManager` **176 star** —— 高级搜索、标签、星级、集成图册、批量操作：<https://github.com/ComfyAssets/ComfyUI_PromptManager>
  - `smart-comfyui-gallery` **392 star** —— 按 prompt/model/LoRA/date 过滤 + 评分 + 虚拟合集：<https://github.com/biagiomaf/smart-comfyui-gallery>
- **怎么实现**：
  1. 新增 `D:\主工作区\outputs\prompts.json`（与现有 `timeline-state.json` / `assets.json` 同级，不新建库）。
  2. 一条 Recipe = `{ id, name, tags, modeId, prompt, params:{aspect,steps,seed,batch}, toggles:{...}, refHashes:[...] }` —— 注意 `refHashes` 用素材库的 sha256 前 16 位（`assets.mjs` 已有），**不是文件路径**（路径会变，hash 不会）。
  3. 「一键套用」= 把这条 Recipe 的 params/toggles/refHashes 一起灌回参数面板与参考图槽位 —— 这是当前工作台完全没有的能力。
  4. 工具：`prompt_save` / `prompt_list` / `prompt_apply`；Agent 生成成功后主动建议存 Recipe。
- **工作量**：**小**（一个 JSON 文件 + CRUD + 套用逻辑，估 250~350 行）
- **优先级**：**P1** —— 直接决定「这次调好的东西下次还能不能用」。

### F13. 模板变量：结构化四段 + 主体标签自动编号

- **解决什么问题**：H3 的提示词是四段式结构化模板（`subject_definitions` / `integrated_multimodal_description` / `overall_soundscape` / `non_diegetic_music`），且必须用 `<Subject N>` / `<Picture N>` 引用素材。手写极易错号：`<Picture 3>` 指向第 4 张图，或者同一角色在不同镜头里变成 `<Subject 2>`。
- **来源**：
  - 本机 `prompt-gate.mjs` 已在硬校验这四段与「不许写『第N张图』」，但它只**拦**不**生成**
  - 艾萝工坊《使用 MiniMax H3 生成音视频》给出的标准三段式写法与职责划分（`subject_definitions` 命名、`retention_analysis` 规定保留特征）：<https://www.erocraft.com/docs/comfycarry/generation/minimax-h3>
  - 《MiniMax H3 提示词大全》（含多素材联合参考的写法）：<https://github.com/AtlasCloudAI/awesome-minimax-h3-prompts>
- **怎么实现**：
  1. 主体标签由 F1 的角色卡**直接推导**：角色 A 永远是 `<Subject 1>`，绑定 `<Picture 1..k>` 是它的定妆图。生成提示词时自动补 `subject_definitions` 段，Agent 只需填 `integrated_multimodal_description`。
  2. 提供 3~5 个内置骨架（文戏 / 武戏 / 产品展示 / 空镜 / 台词戏），骨架里带 `retention_analysis` 的固定句式。
  3. 与 `prompt-gate.mjs` 打通：闸门从「检查四段在不在」升级为「检查编号与角色卡是否一致」—— 错号能被机器抓住。
- **工作量**：**小**（模板字符串 + 编号推导 + 闸门加一条校验，估 200~300 行）
- **优先级**：**P1** —— 它让 F1 的收益翻倍（角色卡不只是塞图，还统一了提示词里的称谓）。

### F14. 反推升级：一次给 3 个候选 + 差异标注

- **解决什么问题**：现在 `timeline_reverse_prompt` 的 `prepare/apply` 是「一问一答」—— 反推一次得到一版，不满意就再来一轮，且不知道两版差在哪。
- **来源**：
  - `FranckyB/ComfyUI-Prompt-Manager` 能从图片/视频的 metadata 里反抽提示词（说明「从产物反推」是普遍需求）：<https://github.com/FranckyB/ComfyUI-Prompt-Manager>
  - `Image-MetaHub` **333 star** 的视觉相似度检索（反推之后要找「像它的其他产物」，靠相似度而不是靠词）：<https://github.com/LuqP2/Image-MetaHub>
- **怎么实现**：
  1. `prepare` 一次返回 3 个写作角度（写实 / 风格化 / 镜头语言导向），`apply` 时可带上 `variantId`。
  2. 已有 `reverse.mjs` 与 M0 的校验器（34/34 已交付）不用动，只加一层「多变体 + diff」。
  3. diff 用现有的 prompt 比对做（`prompt-gate.mjs` 已有 `hash()` 指纹），标注「哪几句不同」，而不是把两段文字整段贴出来。
- **工作量**：**小**（估 150~250 行）
- **优先级**：**P2**

## 五 · 如果只能做 3 个

**选：F1 角色卡、F9 字幕、F8 转场。**

排序依据是「缺口严重度 × 投入产出比 × 是否纯本地」，三个都满足「不装新模型、不重启 ComfyUI、改现有文件就能交付」：

| | 补的是哪件事 | 为什么现在最该做 |
|---|---|---|
| **F1 角色卡** | 像不像同一个人 | 一致性是 AI 短剧的第一痛点。而 **6 个参考图槽位和带 hash 的素材库都已经在跑**，缺的只是「记住谁是谁」这层映射 —— 这是全清单里唯一「底子已铺好、只差一层薄封装」的大收益项。 |
| **F9 字幕** | 看不看得懂 | 缺口 100%（成片零字幕）。依赖已全部就位并**实测过**：`faster_whisper 1.2.1` 可 import、ffmpeg 有 `subtitles`/`ass`、中文字体齐备、提示词里本来就有台词。零云端、零模型下载以外的等待。 |
| **F8 转场** | 接不接得上（观感） | 全清单**投入产出比最高**：本机 ffmpeg 已支持 57 种 `xfade`，只需改 `render.mjs` 一处 filtergraph 分支（现在 grep `xfade` 零命中）。一两百行换掉每一处生硬硬切。 |

**为什么把「更性感」的几个排后面**：

- **F2 首尾帧**是解决一致性的根治手段，但它要新增一条 fl2v 工作流、要标定衔接阈值、要真跑验收（方案书里原本就把它排到 M4）。在 F10 的质检口径落地前做它，等于「改了但不知道有没有变好」。
- **F3/F7 候选审片**价值很高，但它依赖 UI 与数据层改造，属于「一次做对、之后一直受益」的基础设施，适合排在三个 P0 之后的第一批。
- **F11 口型同步**需要额外大模型，且本机是否已装**未验证**；更要紧的是—— 字幕做完之后，口型问题从「看不懂」降级成「不够完美」。
