# 轨道顺序改造 · 20 处硬编码的判定表

> 主人 2026-10-21 定的规格：
> **轨道自上而下：视频 2 → 视频 1 → 音频 1 → 音频 2 → 字幕**
>
> 现状：渲染顺序 = `[...overlay, main, ...audio]`
>       = 视频 2、**字幕**、视频 1、音频 1、音频 2
>       ⇒ 字幕在中间，要挪到最下。

---

## 一 · 核心认知：两种「顺序」完全不是一回事

```
① 画面叠加顺序（z-order）
   overlay 在上、main 在下 —— 这是【渲染】语义。
   ★ 绝对不能在渲染侧动：动了字幕会盖住画面、或者画面盖住字幕。

② UI 轨道行顺序（用户从上往下看到的行序）
   —— 这才是主人要改的。
```

两者现在共用同一个 `[...overlay, main, ...audio]` 表达式，所以改之前必须逐处判定这一处属于哪一种。

## 三 · 怎么改才不会再漏

绝不逐处手写 `[...overlay.filter(...), main, ...audio]` —— 那样 14 处里漏一处就是
「点击位置与视觉错位」这种极难查的 bug（本项目 §6.43 的典型场景）。

**做法：加一个导出函数 `getDisplayTracks()`，让 14 处都调它。**

```ts
// lib/timeline/display-order.ts（新文件）
export function getDisplayTracks({ tracks, // SceneTracks
}: { tracks: SceneTracks }): TimelineTrack[] {
  // UI 顺序：视频2（overlay 里的 video）→ 视频1(main) → 音频 → 其余 overlay（字幕等）
  const overlayVideos = tracks.overlay.filter(t => t.type === "video");
  const overlayOthers = tracks.overlay.filter(t => t.type !== "video");
  return [...overlayVideos, tracks.main, ...tracks.audio, ...overlayOthers];
}
```

**为什么按 type 分流而不是按索引**：
- 用户可能再加第 3 条 overlay 视频，按索引会错位
- 按 `type === "video"` 分流，任何数量都对

**为什么字幕排最后而不是排中间**：
- 主人明确选择「视频2 视频1 音频1 音频2 字幕」
- 与 CapCut 的「字幕在画面之上」不同，但这是主人的明确偏好，不按行业惯例改

## 四 · 验收判据

```
① 源码级：20 处里 14 处都调 getDisplayTracks，没有一处再手写 [...overlay, main, ...audio]
   （渲染侧那 6 处保留原样，并在注释里标注「这是渲染顺序，别动」）
② 运行时：浏览器里轨道行的 y 坐标自上而下必须是
   视频2 < 视频1 < 音频1 < 音频2 < 字幕
③ 命中测试一致：点击「音频1」的轨道区域，选中的必须是音频1（不是别的）
   —— 这一条最关键：getDisplayTracks 同时供渲染与命中，两边同一个值才不会错位
```
