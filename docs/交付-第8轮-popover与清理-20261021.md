## 一 · 发现并修掉的两个真缺陷

### 缺陷 1：多个浮层可以同时开着

```
实测：连续点两张卡的「更多操作」
  → 页面上出现 2 个 z-index:99999 的浮层
  → 一个在 y=603，一个在 y=1461（视口高 914，完全在屏幕外）
  → 第一个不会消失
```

**根因**（`AssetLibrary.js` 的 `CardMoreButton`）：

```js
const onDown = (e) => {
  if (btnRef.current?.contains(e.target)) return;
  if (e.target?.closest?.("[data-wb-card-more]")) return;   // ← 这里
  setOpen(false);
};
```

第二句本意是「点浮层内部不关闭」，但**所有卡的「更多」按钮都带 `[data-wb-card-more]`**，
所以点另一张卡的按钮时也命中这条 ⇒ 不关自己。

**修法**：全局单例 id + 自定义事件。

```js
// 打开时
const prev = window.__WB_CARD_MORE_OPEN__;
if (prev && prev !== instanceId.current) {
  window.dispatchEvent(new CustomEvent("wb:card-more-open", { detail: instanceId.current }));
}
window.__WB_CARD_MORE_OPEN__ = instanceId.current;

// 监听
const onOtherOpen = (e) => { if (e.detail !== instanceId.current) setOpen(false); };
window.addEventListener("wb:card-more-open", onOtherOpen);
```

**实测修复后**：

```
连续点 3 张不同卡的「更多操作」：
  第 1 次：浮层数=1  allInViewport=true
  第 2 次：浮层数=1  allInViewport=true
  第 3 次：浮层数=1  allInViewport=true
```

### 缺陷 2：浮层可能跑到视口外

```
实测：抓到一个 top:1461px 的浮层（视口高 914）
根因：const above = anchorRect.top - H - 4;
      if (above >= GAP) return above;      ← anchorRect.top=1461 时 above=1217
                                              1217 ≥ 8 成立 ⇒ 直接返回 1217，仍在视口外
      最后那条 clamp 只在「above < GAP」时才执行，兜不住这种情况
```

**修法**：先算「想要的位置」，最后**统一**钳进 `[GAP, innerHeight - effH - GAP]`；
`effH` 用 `min(H, 视口高 - 2*GAP)`，避免视口比浮层还矮时 clamp 区间反向。

## 七 · 本轮教训

### 「兜底分支」不能只在某个前提下才执行

缺陷 2 的写法是：

```js
if (above >= GAP) return above;                          // 提前返回
return Math.max(GAP, Math.min(below, vh - H - GAP));     // 兜底
```

看起来有兜底，但**兜底只在提前返回没命中时才跑**。
而提前返回的条件（`above >= GAP`）在「锚点本身就在视口外」时恰好成立。

⇒ 判据：凡是「先算、中间有个分支提前返回、最后还有个 clamp」的结构，
  要问：**提前返回的那条路，它的结果需要被 clamp 吗？**
  需要的话，就把 clamp 提到最后、对所有路径统一生效。

### 用户能触发的 vs 脚本能触发的

缺陷 2 我是用脚本点击**视口外**的按钮才复现的 —— 真实用户点不到不可见元素。
所以它严格说不是「用户能触发的 bug」。

但我仍然修了，理由是：
- 成本低（改 10 行）
- 能兜住「窗口 resize 时浮层已打开」这类真实场景
- 反过来，缺陷 1（多浮层）**是**用户能触发的，那个必须修

⇒ 两者都修，但在报告里**如实区分**哪个是用户可触发、哪个是防御性修复。
