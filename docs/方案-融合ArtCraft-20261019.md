## 二、它被设计成「可嵌入」——这是最关键的好消息

`src/index.ts`（1250 行）的公开 API 明确分三层：

```ts
// ① 整个编辑器外壳（大多数宿主只挂这个）
export { VideoEditor } from "./lib/VideoEditor";

// ② 或自带外壳，只用内层
export { EditorProvider, useEditorAdapters } from "./lib/EditorProvider";

// ③ 由宿主实现 6 个 adapter —— 这是干净的接缝
export type {
  ProjectStorageAdapter,   // 项目存取
  MediaSourceAdapter,      // 媒体文件来源
  AssetGalleryAdapter,     // 素材画廊
  AuthUserAdapter,         // 登录用户
  ExportSinkAdapter,       // 导出落点
  ToastAdapter,            // 提示
} from "./lib/adapters";

// ④ 还给了默认实现（可直接跑）
export {
  createDefaultAdapters,
  createIndexedDBProjectStorage,
  createLocalFileMediaSource,
  anonymousAuthUser,
  downloadExportSink,
  consoleToast,
} from "./lib/adapters/default";
```

**⇒ 我们不需要改它一行代码，只要实现这 6 个 adapter 就能接上 dsh-editor 的 store。**

## 三、架构质量：命令模式 + 分离的 store

### 命令层是纯 TS，零 React

```ts
// commands/base-command.ts（全文 1,096 B）
export abstract class Command {
  abstract execute(): CommandResult | undefined;
  undo(): void { throw new Error("Undo not implemented for this command"); }
  redo(): CommandResult | undefined { return this.execute(); }
}
```

53 个 command 覆盖：media / project / scene / timeline（clipboard、element、effects、keyframes、masks、track）

**⇒ 命令层可以脱离 React 单独跑。**

### store 只依赖 zustand

```ts
// editor/editor-store.ts
import { create } from "zustand";
export const useEditorStore = create<EditorState>()(...)
```

全部 5 个 editor 层文件：`cancel-interaction` / `editor-store` / `panel-store` / `use-editor` / `use-menu-preview`。

### 项目数据结构

```ts
TProject {
  metadata: { id, name, duration, createdAt, updatedAt }   // 全有
  scenes: TScene[]                                         // ★ 我们没有这层
  currentSceneId
  settings: { fps, canvasSize, background }                // 我们部分有
  version
  timelineViewState: { zoomLevel, scrollLeft, playheadTime }  // ★ 我们没有
}
```

**差异：它有 scene 层（一项目多场景/序列），我们是平铺 tracks。**

## 四、代价（必须让主人先看清）

### 4.1 依赖清单（53 个）

**必留（视频编辑器主体需要）**

```
mediabunny           视频解封装/编码（核心，不可省）
opencut-wasm         WASM 帧处理（timeline/retime/effects 依赖）
zustand              状态

@dnd-kit/core + sortable + utilities               拖拽
react 18.3.1 + react-dom                           框架
```

**可剥（只要不挂「3D 场景」和「绘图」面板）**

```
three 0.171          3D 场景（PageScene 用，编辑器主体不需要）
@sparkjsdev/spark    3D 高斯泼溅
konva                2D canvas 绘图（PageDraw 用）
posthog-js           埋点
@react-oauth/google  第三方登录
embla-carousel*      轮播
qrcode.react         二维码
react-router-dom     路由（我们自己是 slot 挂载）
react-helmet         head 管理
framer-motion        动画（可换 CSS transition）
@react-spring/web    动画
detect-gpu           GPU 探测
culori / dayjs / lodash / uuid / eventemitter3   小而杂，留着无妨
```

### 4.2 体积估算

```
当前 lib/client.js                     208 KB
接入后（剥掉 three/spark/konva 等）   ≈ 800 KB ~ 1.2 MB
```

**这是硬代价。** 但注意：工作台的 bundle 只在打开「视频工作台」tab 时加载，不影响 DSH 主界面。

### 4.3 CSS 是最大的技术障碍

```
video-editor 自己【零个】css 文件
样式全部来自 Tailwind 类名（如 className="flex items-center gap-2"）
基础样式在 frontend/apps/artcraft/app/src/styles/{base,normalize,tailwind}.css
```

**⇒ 必须新增一条构建链：**

```
① Tailwind 编译（扫 video-editor 的 tsx，产出 utility 类）
② 加作用域前缀（所有选择器包进 .comfy-wb-artcraft 下）
③ 运行时注入 <style>（DSH 没有 CSS 通道，这是硬约束 §3.4）
```

**风险：** 步骤 ② 有成熟的 `postcss-prefix-selector`，但 Tailwind 的 CSS 变量（`--tw-*`）会与 DSH 的 `--dsw-*` 并存 —— 需实测是否互相干扰。

## 五、分期方案（我的建议）

### 第 0 期 · 可行性验证（1 天，不动现有代码）

```
1. 把 video-editor 源码 + 必需依赖拷到独立目录
2. 剥依赖：注释掉 PageScene/PageDraw 相关的 import，看是否还能编译
3. 配 Tailwind 构建 + 作用域前缀，验证 CSS 不与 DSH 冲突
4. 写一个最小 adapter 实现（读本地 mp4 + 导出到本地）
5. 起一个独立 HTML 页面挂 <VideoEditor>，跑通「导入→裁剪→导出」
```

**产出：一个能跑的 demo + 一份「实际体积/CSS 冲突/编译问题」清单。**

**这一步失败就不用往下走。** 我预估成功率 70%（CSS 是主要变数）。

### 第 1 期 · 并行接入，不动现有粗剪（2-3 天）

```
新增 tab「精剪」，挂 ArtCraft 的 VideoEditor
adapter 接 dsh-editor 的 store：
  ProjectStorageAdapter → /timeline/snapshot + /timeline/cmd/*
  MediaSourceAdapter    → 现有素材库 + ComfyUI 产物
  ExportSinkAdapter     → 现有 /timeline/cmd/export（ffmpeg）
  AssetGalleryAdapter   → 现有 /comfy-assets/library
保留现有「粗剪」tab 作为回退
```

### 第 2 期 · 替代粗剪（第 1 期验证通过后）

```
删掉现有粗剪 UI，把 26 个验收里仍有意义的迁到新实现
Agent 工具链（15 个 timeline_* 工具）继续复用 —— 它们操作的是 store，
不依赖 UI 是哪套
```

### 第 3 期 · 补协同层（ArtCraft 没有的东西）

```
ArtCraft 是单机编辑器，没有「Agent 与用户同时操作」的概念
我们的优势在这里：store + 命令 + SSE + who 区分已有
⇒ 在 adapter 层做「操作广播」，让 Agent 的改动落到同一个 project
```

## 六、回退路径

```
第 0 期失败   → 什么都不改，现有粗剪继续用
第 1 期失败   → 删掉新 tab，现有粗剪不受影响
第 2 期失败   → 恢复粗剪 tab（代码保留到第 2 期结束）
```

**关键纪律：第 1 期之前不动任何现有代码。**

## 七、需要主人确认的三件事

```
① 接受第 0 期的 1 天投入（只出 demo，可能证明不可行）

② 接受最终体积从 208KB 涨到约 1MB
   （只在打开视频工作台 tab 时加载）

③ 「融合」的含义确认：
   · 是「ArtCraft 的时间轴 + 我们的 ComfyUI 生成能力」吗？
   · 还是「连它的云端模型调用（fal/grok/sora）也接进来」？
     ← 后者我们有自己的 ComfyUI 本地链路，接云端是另一条路
```

## 八、我此刻的判断

**架构上完全可行，代价主要在 CSS 和体积。**

ArtCraft 的 author 把 video-editor 做成 adapter 架构，本意就是给别人嵌 —— 这个信号很强。命令层纯 TS、store 只依赖 zustand，说明它没有把 React 焊进逻辑里。

**真正的不确定性只有一个：Tailwind 的 CSS 能不能干净地作用域隔离。** 这一点第 0 期一天内就能验证。

**我建议做第 0 期。** 因为：
- 投入小（1 天）
- 结果明确（能跑 demo 或明确不能）
- 不碰现有代码（零风险）
- 如果成功，后面就有清晰的路
