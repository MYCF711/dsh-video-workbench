### 问题 1. 媒体校验只验文件头结构，不验载荷 —— 7 种格式全穿透 ★最严重（绕过第 4 项）

- **请求体（关键部分）**：
  ```json
  {"modeId":"qwen21-edit","prompt":"x","steps":4,
   "files":{"ref_image_0":{"base64":"<见下表>","filename":"a.png"}}}
  ```
- **实测返回原文**（每一行都是真提交，均返回 promptId）：

| 格式 | 载荷 | 返回 |
|---|---|---|
| PNG | 8 字节签名 + `IHDR` + `GARBAGEGARBAGE…` | `{"jobId":"comfy-mve8j5gw-9ygr6k","promptId":"ae792dea-e536-4ddc-9765-78afc0c9184b","nodes":18}` |
| WEBP | `RIFF`+size+`WEBP`+垃圾 | `{"promptId":"38fc5f53-5325-48f6-a1d8-b456f3eedd77","nodes":18}` |
| WAV | `RIFF`+size+`WAVE`+垃圾 | `{"promptId":"f66714c0-05de-4265-a57b-09640aee3f8d","nodes":18}` |
| GIF | `GIF89a`+垃圾 | `{"promptId":"62910ddb-f0f1-44a4-bb69-71a2518f8522","nodes":18}` |
| JPEG | `FFD8FF`…`FFD9` 中间垃圾 | `{"promptId":"a864138f-eb92-47de-9392-c19fab8188c0","nodes":18}` |
| WEBM | `1A45DFA3`+垃圾 | `{"promptId":"4a16f343-1c04-47fa-b759-f9bd129a9477","nodes":18}` |
| BMP | `BM`+声明 size 吻合+垃圾 | `{"promptId":"66c978bb-0014-4ac9-a877-a461c2f6c299","nodes":18}` |

- **极端案例（16 字节）**：PNG 签名(8B) + `IHDR`(4B) + 全零(4B)，**图像数据 0 字节**
  ```
  base64: iVBORw0KGgoAAAANSUhEUkdBUkJBR0VHQVJCQUdFR0FSQkFHRQ==
  → {"promptId":"15c23e3b-ee8b-408b-a75c-b8e85a4f7d5f","nodes":18}
  ```

- **危害链（有原始证据）**：垃圾先**落盘**到 ComfyUI 的 input 目录，再在 LoadImage 阶段炸掉：
  ```
  D:\Comfy-Desktop\ComfyUI-Shared\input\ 实测 19 个我造的垃圾文件：
    16 wb_ref_image_0_a_74bo38.mp4
    16 wb_ref_image_0_a_q2wry4.png
    17 wb_ref_image_0_a_og0ufm.mp3
    18 wb_ref_image_0_a_c2m36n.bmp
    ...
  37 wb_ref_image_0_a_2gmqbf.png

  /history/ae792dea-...:
    status_str=error  completed=False
    EXEC_ERROR node=470 type=LoadImage
      msg=cannot identify image file 'D:\...\input\wb_ref_image_0_a_wh9x20.png'
  ```
  ⇒ 校验的目的（「让错误停在入口、说明白」）没有达成：错误仍然发生在 LoadImage，
  且**垃圾文件已经污染了 ComfyUI 的 input 目录**（需人工清理）。

- **为什么算绕过**：`looksLikeMedia()`（index.js:217–266）只看前 16 字节内的结构字段，

- **严重程度：高**

- **建议修法**（任一即可，推荐 1+2）：
  1. **真解码**：`sharp`/`jimp` 解一次图像，抛错即拒。这是唯一可靠的判据。
  2. **加重试上限外的结构尾校验**：至少校验 PNG 的 `IEND` 块存在、JPEG 的 SOF 段、
     WebP 的 `VP8 `  chunk —— 能把上面 7 例全拦掉（但不解决根本）。
  3. 上传前不落盘：先写临时目录校验通过再交给 `/upload/image`。

### 问题 2. MP3 的 ID3 分支只查 4 个字节（绕过第 4 项，同根因）

- **请求体**：`{"modeId":"qwen21-edit","prompt":"x","steps":4,"files":{"ref_image_0":{"base64":"SUQzBEdBUkJBQUdFQllURVM=","filename":"a.mp3"}}}`
  （解出：`ID3` + `0x04` + `GARBAGEBYTES`）
- **返回原文**：`{"jobId":"comfy-mve8mrt...","promptId":"b73702bc-e064-4d49-a1e5-8ace243bd3dd","nodes":18}`
- **反证（证明是这条分支而不是别的原因）**：
  - `ID3`+`0x09`+垃圾 → **拒绝**（`前 8 字节：49 44 33 09 47 41 52 42`）
  - `ID3`+`0x02`+垃圾 → **通过**
  - `XYZ`+垃圾 → **拒绝**
  ⇒ 判据就是 index.js:260–262 的 `buf[3] === 2|3|4`，一个字节即可伪造。
- **为什么算绕过**：与 #1 同源（只查头部），单列是因为它只有 **4 字节**有效校验，
  比其它格式更弱。
- **严重程度：高**（与 #1 合并计为同一类根因）

### 问题 3. 提示词没有长度上限（8 项之外的缺失校验）

- **请求体**：`{"modeId":"krea2","prompt":"aaa…(1MB)","steps":4}`
- **返回原文**：
  ```
  1MB  → {"jobId":"comfy-mve8mruc-x6erwf","promptId":"4a91d998-1183-4e51-8ce6-9bf196592b36","nodes":17}
  10MB → {"jobId":"comfy-mve8is7x-tl5lmy","promptId":"41b3ccea-45a8-4129-91b2-ea0fd6412dc5","nodes":17}
  ```
- **为什么算绕过**：8 项校验里没有「长度」这一项。1MB / 10MB 提示词直接进
  `CLIPTextEncode.text`，会被 tokenizer 整段处理（浪费显存与时间，且模型只会看到
  前 77/512 token）。
- **边界**：请求体 >64MiB 会被 `readBody` 的 64MiB 上限强断（实测 68,157,480 字节
  → `远程主机强迫关闭了一个现有的连接`）。也就是说 1MB~64MB 之间全部放行。
- **严重程度：中**

- **建议修法**：`if (params.prompt.length > 8000) throw ...`（8000 字符已远超 CLIP 上限）。

## 该通过但被误拒的

### 问题 4. 提示词白名单漏掉整个 Unicode `\p{S}`（符号）类别（第 1/8 项副作用）

- **现象**：以下**有明确视觉内容**的提示词全被拒：
  ```
  [REJECT] prompt=$    → {"error":"提示词不能为空（只有空白或不可见字符）—— 会生成随机的图"}
  [REJECT] prompt=+    → 同上
  [REJECT] prompt=∑    → 同上
  [REJECT] prompt=℃    → 同上
  [SUBMIT] prompt=%%%  → {"promptId":"909d220b-..."}   ← % 是 P 类，能过
  [SUBMIT] prompt=$5   → {"promptId":"9640a6f5-..."}   ← 有数字就能过
  ```
- **根因（本地复算，与线上逐项一致）**：`text-guard.mjs:50–63` 的 `VISIBLE` 白名单是
  `\p{L}` + `\p{N}` + `\p{P}` + 6 个硬编码符号区段，**没有 `\p{S}`**。
  实测逐个编码：

  ```
  ★拒绝  $   U+0024  S类     通过  %   U+0025  P类
  ★拒绝  +   U+002B  S类     通过  •   U+2022  P类
  ★拒绝  =   U+003D  S类     通过  …   U+2026  P类
  ★拒绝  <   U+003C  S类     通过  §   U+00A7  P类
  ★拒绝  >   U+003E  S类     通过  ©   U+00A9  S类（硬编码，侥幸）
  ★拒绝  |   U+007C  S类     通过  ¥   U+00A5  S类（硬编码，侥幸）
  ★拒绝  ~   U+007E  S类     通过  🐱  U+1F431 S类（在 emoji 区段）
  ★拒绝  ^   U+005E  S类
  ★拒绝  ∑   U+2211  S类
  ★拒绝  ℃   U+2103  S类
  ★拒绝  √   U+221A  S类
  ★拒绝  ∞   U+221E  S类
  ★拒绝  ≈   U+2248  S类
  ★拒绝  ≠   U+2260  S类
  ```
  ⇒ **凡是纯符号提示词，只有落在那 9 个硬编码字符/3 个区段里的才能过，其余一律误拒。**
- **为什么算问题**：`+` `=` `~` `^` 是正常可输入字符。用户写 `a = b` 能过（有字母），
  但单独调符号就报「不能为空」—— 文案还是错的（它不为空）。
- **严重程度：中**（不导致错误提交，但会误拒合法输入且给出误导性文案）

- **建议修法**：白名单加 `\p{S}`，再单独用 `LETTER_BUT_BLANK`/`BRAILLE` 排除空白符号：
  ```js
  "\\p{L}\\p{N}\\p{P}\\p{S}"   // S 覆盖 $ + = < > | ~ ^ ∑ ℃ ¥ € 等
  ```
  （`U+2800` 盲文已由 `BRAILLE` 单独排除，不会被 `\p{S}` 误放行 —— 已验证。）
