### 2 处误报（已加过滤规则，不是文案）

```
"extends BoxSelectionSnapshot"   ← interface X extends Y 被 JSX 文本正则误抓
"extends BaseNode"               ← 同上
"IDBRequest"                     ← run: (store) => IDBRequest<T> | void
                                   提取时 < > 被剥掉，剩裸类型名
```

过滤规则（`isLikelyCodeFragment`）：

```js
if (/^(extends|implements|interface|type|declare)\b/.test(s)) return true;
if (!/\s/.test(s) && /^[A-Z][A-Za-z]*(IDB|HTML|SVG|URL|API|DOM|CSS|JSON|HTTP|...)[A-Za-z]*$/.test(s)) return true;
```

★ 不能简单放宽「单个驼峰词」那条的阈值 —— 那会把 `Spotlight` 这类真文案也吞掉。

### 1 处开发者报错信息（不该翻）

```js
// EditorProvider.tsx:44-47
throw new Error(
  "useEditorAdapters must be used inside <EditorProvider>. " +
    "Mount your <VideoEditor> below an <EditorProvider>.",   ← 提取出 "below an"
);
```

**判据：用户看得见 ⇒ 要翻；只有开发者看得见 ⇒ 不翻。**
翻译编程错误信息反而降低可搜索性（开发者会拿英文去搜）。

处理：
1. 同行有 `Error(` / `console.*` → 跳过
2. 多行 throw 的续行（整行只是 `+` 连接的字符串字面量）→ 也跳过

## 四 · 本轮的方法论教训

### 「扫过了」不等于「扫描器是好的」

我这次是在**盘点脚本登记情况**时偶然发现那个脚本坏的。
如果不是做这个盘点，它会一直躺在那儿，而我每轮都拿「另一个脚本通过」当证据。

⇒ 判据：任何「我说已经清理干净」的结论，必须能指出
   ① 用的是哪个脚本
   ② 那个脚本最后一次真实通过的输出
   ③ 它是否在总验收里

### 同一个坑（§6.44a）我踩了第二次

AGENTS 里明确写着「未登记进总验收的脚本 = 心理安慰」，
我这轮之前有 1 个脚本漏登记，而且它是坏的。

⇒ 这不是「不知道」，是「知道但没执行」。
  所以这条应该做成**自动检查**：新增脚本时 `verify-all` 会报「有脚本未登记」
  （目前靠我这个盘点动作，下次会话可能又忘）。
